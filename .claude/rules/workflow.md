# Dynasty Sim

Текстовый симулятор династии по мотивам режима авантюриста из Crusader Kings 3. Вымышленный мир по законам нашего, старт около 1700 года. Главное: процедурные события и история, которая складывается из случайностей и решений игрока. Заготовленного сюжета нет. После смерти главы рода игрок продолжает за наследника.

Владелец: Тим, дизайнер. Код не читает, принимает работу по описаниям, хронике симуляции и игре.

## Стек
TypeScript, игра в браузере (Vite). Ядро симуляции отдельно от интерфейса и запускается без него. Контент в YAML со строгой схемой и валидатором. Сохранения в JSON. Вся случайность через seed. Детали в CLAUDE.md и docs/DECISIONS.md.

## Язык
С Тимом и в docs пишем по-русски. Код, комментарии, имена, коммиты и тексты игры на английском.

## Источники правды
docs/GDD.md дизайн, docs/ROADMAP.md задачи, docs/DECISIONS.md решения, docs/STATUS.md текущее состояние, docs/CHANGELOG.md история.
1. В начале задачи прочитай STATUS и относящиеся к ней записи DECISIONS.
2. Принятое решение молча не меняй. Нужно другое: предложи новую запись в DECISIONS со ссылкой на старую и причиной.
3. Перед завершением обнови CHANGELOG и STATUS, новые решения запиши в DECISIONS.

## Как работает тред
1. Одна задача из ROADMAP на тред, ветка от main, один PR.
2. Коммить и пушь после каждого осмысленного шага: песочница может потерять незакоммиченное.
3. Готово, когда тесты зелёные, валидатор контента проходит, прогон симуляции без ошибок, доки обновлены.
4. Перед мержем отдай PR субагенту reviewer. Он не видел, как писался код, и проверяет по своему чек-листу.
5. Мержи в main сам (squash), когда CI зелёный и reviewer одобрил. Без force-push. CI и правила веток не меняй без согласия Тима.
6. Не хватает доступа, ключа или информации: в первом сообщении скажи, чего именно нет, и остановись. Не подменяй, не мокай, не угадывай.

## Модели и роли
Треды по умолчанию на Sonnet 5.5, effort medium. Остальное по ролям из .claude/agents:
· architect, opus, high: план этапа, архитектура, сложные баги
· implementer, sonnet, medium: код по готовому плану
· content-writer, sonnet, medium: события пачками по схеме
· scout, haiku, low: поиск по коду, обновление доков, прогон тестов и симуляции со сводкой
· reviewer, opus, high: независимая проверка перед мержем
Тред с архитектурной задачей запускай на Opus. Fable только по прямой просьбе Тима.

## Координация (отдельные облачные сессии без проекта)
Каждый тред — отдельная облачная сессия. Общей памяти между ними нет: всё, что должно пережить сессию, лежит в репозитории.
1. Общая память — репозиторий: CLAUDE.md, это правило, docs/. Сессия начинает с STATUS и нужных записей DECISIONS и заканчивает обновлением STATUS и CHANGELOG. Важное в чате не оставляй.
2. Этап начинается с плана от architect. План ложится в docs/ROADMAP.md отдельным PR: задачи с ID, модулем, критериями готовности. Код по этапу пишется только после «ок» Тима.
3. Задача занята, если по её ID есть открытый PR (заголовок `[2.3] …`). Перед стартом проверь открытые PR. Черновой PR открывай после первого коммита.
4. Внутри утверждённого плана задачи запускай сам, новыми облачными сессиями. Не больше 3 одновременно и только из разных модулей. Модель сессии выбирай по роли задачи. Промпт сессии самодостаточный: ID, ссылка на план, границы модуля, критерии готовности, «работай по .claude/rules/workflow.md». Дочерние сессии новых сессий не запускают. Если запускать сессии нечем, скажи Тиму и дай готовые промпты.
5. За дочерними сессиями следи по их PR и состоянию сессии, не опросом в цикле. Сессия, открывшая PR, сама доводит его до мержа.
6. Параллельные PR правят общие доки. Перед мержем влей свежий main и сведи конфликты, ничего чужого не теряя.
7. Отчёт Тиму короткий: что сделано, что сломалось, что ждёт его решения. Без пересказа шагов.
8. Новая задача — новая сессия. Старую оживляй только для правок её же PR.
9. Вопросы Тиму задавай инструментом вопросов: 2–4 варианта, первый — рекомендуемый с пометкой «(Recommended)», у каждого одна строка о том, к чему он ведёт. Несрочные вопросы записывай в STATUS в том же виде.
10. Идеи Тима хранятся в docs/IDEAS.md. Если Тим высказал идею мимоходом в другой сессии, та сессия записывает её туда в своём PR. Architect в начале этапа просматривает IDEAS.md и предлагает Тиму идеи, подходящие к этапу. Идеи не решения: записанная в IDEAS.md идея в игру не входит, пока Тим не сказал «берём» и её не перенесли в GDD, ROADMAP или DECISIONS; статус «взята» с указанием, куда перенесена, ставит сессия, делающая перенос. Для постоянной сессии «Идеи» п. 1 «Как работает тред» и п. 8 действуют так: она живёт долго, задачи в ROADMAP у неё нет, идеи записывает пачками отдельным PR `[ideas] …` от свежего main и завершает его как обычно.
