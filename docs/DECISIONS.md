# Решения

Принятое решение не меняется молча. Нужно другое — новая запись со ссылкой на старую и причиной, а у старой статус «заменено D-NNN».

Формат: **D-NNN. Название** — дата, статус; контекст, решение, последствия.

---

## D-001. Стек
2026-10-15 · принято

**Контекст.** Игра текстовая, в браузере. Тим принимает работу по хронике, поэтому симуляция должна запускаться без интерфейса.

**Решение.**
- TypeScript (strict), игра в браузере на Vite. Node 22 для инструментов.
- Ядро `src/core` отдельно от интерфейса `src/ui`: свой tsconfig без DOM и Node, правила проверяет тест архитектуры.
- Тесты — Vitest. Скрипты в `tools/` запускаются через tsx.
- Схема контента — zod 4, парсер YAML — `yaml` (YAML 1.2).
- Интерфейс пока без фреймворка, обычный DOM. Вопрос фреймворка — к задаче 2.8.
- Версии зависимостей закреплены точно. TypeScript 7 используется только для проверки типов (`tsc --noEmit`). Если он помешает инструментам, откат на 6.0 без других изменений.
- Сохранения — JSON.

**Последствия.** Ядро можно гонять в Node (прогоны, тесты) и в браузере одним и тем же кодом. Любая зависимость ядра от браузера или диска — ошибка сборки.

## D-002. Контент как данные
2026-10-15 · принято; уточнено D-052

**Контекст.** Игра держится на большом количестве событий и действий. Их должны писать агенты и Тим без программирования.

**Решение.**
- Контент лежит в `content/` в YAML. Каждый файл — объект с ключами `settings`, `names`, `actions`, `events`; файлы сливаются в алфавитном порядке пути.
- Схема — `src/core/content/schema.ts`: неизвестные поля запрещены, числа целые, id в `lower_snake_case`.
- Загрузчик проверяет перекрёстные ссылки, уникальность id и плейсхолдеры в текстах. Ошибка указывает файл и путь до поля.
- Ядро получает тексты файлов, а не читает диск. Node-инструменты читают `content/` с диска, браузер подключает те же файлы при сборке.
- Все тексты игры, включая системные (смерть, наследование), — в контенте, не в коде.

**Последствия.** `npm run validate` — обязательная проверка в CI. Новое поле контента добавляется в три места: схема, загрузчик, плохой пример в тестах.

## D-003. Seed и детерминизм
2026-10-15 · принято

**Контекст.** Историю нужно воспроизводить: для отладки, баланса и разговора о конкретном прогоне.

**Решение.**
- Вся случайность ядра — через генератор sfc32 (`src/core/rng.ts`), seed разворачивается через splitmix32. Seed — целое от 0 до 4294967295.
- Состояние генератора хранится в `GameState` и сохраняется вместе с игрой, поэтому загрузка продолжает ту же историю.
- В ядре запрещены `Math.random`, `Date`, `performance` и трансцендентные функции `Math` (`exp`, `pow`, `log`, `sin`…), так как их результат может отличаться между движками. Вероятности — целые дроби (`chancePer(r, n, d)`), таблицы — целые числа.
- Состояние — чистый JSON: без классов, `Map`, `undefined`.
- Бот для прогонов использует свой поток (`seedRng(seed, 1)`) и не сдвигает мировой. Функции-запросы случайность не тратят.

**Последствия.** Одинаковый seed и одинаковый контент дают одинаковую хронику байт в байт; это проверяют тесты. Любое изменение контента меняет хроники, поэтому «золотых» снимков нет.

## D-004. Роли моделей
2026-10-15 · принято

**Контекст.** Работа идёт отдельными облачными сессиями и субагентами. Нужен баланс качества и стоимости.

**Решение.** Сессии по умолчанию на Sonnet 5.5, effort medium. Субагенты в `.claude/agents/`:

| Агент | Модель | Effort | Назначение |
|---|---|---|---|
| architect | opus | high | план этапа, архитектура, сложные баги |
| implementer | sonnet | medium | код по готовому плану |
| content-writer | sonnet | medium | события пачками по схеме |
| scout | haiku | low | поиск, обновление доков, прогоны со сводкой |
| reviewer | opus | high | независимая проверка перед мержем; только чтение и проверки |

Сессия с архитектурной задачей — на Opus. Fable — только по прямой просьбе Тима.

**Последствия.** Модель и effort заданы во frontmatter агентов. Reviewer не может править файлы (`disallowedTools: Write, Edit`). Ограничение его Bash командами проверок задано инструкцией, а не настройкой: Claude Code не поддерживает такие шаблоны в `tools`.

## D-005. Язык
2026-10-15 · принято

**Решение.** С Тимом, в docs, в описаниях PR, в CLAUDE.md и инструкциях агентов — по-русски. Код, комментарии, имена, сообщения коммитов и тексты игры — на английском.

**Последствия.** Хроника (текст игры) — на английском, сводки по ней для Тима — по-русски.

## D-006. Календарь
2026-10-15 · принято

**Решение.** Время — целый номер дня; день 0 — 1 января 1700 года. Календарь григорианский: 1700 и 1800 годы не високосные. Даты до 1700 года отрицательные (на них приходятся даты рождения). Шаг симуляции — один день.

**Последствия.** Возраст считается по датам, а не делением на 365. Если понадобится юлианский календарь для отдельных держав, это будет отображение поверх номера дня.

## D-007. Временный наследник до этапа 4
2026-10-15 · принято (решение Тима)

**Контекст.** В каркасе один персонаж, а прогон рассчитан на 300 лет.

**Решение.** Когда глава рода умирает, появляется сгенерированный взрослый наследник (возраст из `settings.heirAge`, та же фамилия). Ему переходят деньги, больше ничего. Текущее действие прерывается.

**Последствия.** Прогоны идут все 300 лет и проверяют календарь, смертность и скорость. Заглушку заменит этап 4 «Династия».

## D-008. Координация через репозиторий
2026-10-15 · принято

**Контекст.** Каждый тред — отдельная облачная сессия Claude Code без общего проекта и общей памяти.

**Решение.**
- Общая память — только репозиторий: CLAUDE.md, `.claude/rules/workflow.md` (загружается в каждую сессию), docs/.
- Задача занята, если по её ID есть открытый PR `[ID] …`.
- Ведущая сессия запускает задачи утверждённого плана новыми облачными сессиями: не больше 3 одновременно, только из разных модулей, с самодостаточным промптом. Дочерние сессии новых не запускают.
- Сессия, открывшая PR, сама доводит его до мержа.

**Последствия.** Всё, что нужно следующей сессии, должно попасть в docs до мержа. Параллельные PR могут конфликтовать в STATUS и CHANGELOG: перед мержем вливается свежий main.

## D-009. Масштаб карты
2026-10-15 · принято (решение Тима)

**Решение.** Карта — средний регион с морем: 40–60 провинций, 15–25 городов, побережье и внутреннее море. Этого хватает морской торговой державе и султанской с её портами, а вручную такую карту ещё можно проработать.

**Последствия.** Задача 1.6 выбирает в Azgaar регион этого размера. Конкретный регион и формат импорта решаются там же.

## D-010. Пол персонажей, браки и дети
2026-10-15 · принято (решение Тима); уточнено D-034; уточнено D-055

**Решение.** Пол персонажей появляется на этапе 2, в задаче 2.3. Браки, дети и правила наследования — на этапе 4, вместе с династией.

**Последствия.** После 2.3 тексты могут использовать местоимения, а запрет «без местоимений» снимается в той же задаче — в CLAUDE.md и в `.claude/agents/content-writer.md`. До этапа 4 наследник остаётся временным (D-007).

## D-011. Состав CI
2026-10-15 · принято (решение Тима)

**Решение.** CI на каждый PR и push в main: проверка типов, тесты, валидатор контента, прогон на 50 лет (seed 1), сборка. Хроника прогона прикладывается к результату.

**Последствия.** Менять состав CI — только с согласия Тима (см. `.claude/rules/workflow.md`).

## D-012. Формат вопросов Тиму
2026-10-15 · принято (решение Тима)

**Решение.** Вопросы Тиму задаются инструментом вопросов: 2–4 варианта, первый рекомендуемый с пометкой «(Recommended)», у каждого одна строка о последствиях. Несрочные вопросы записываются в STATUS в том же виде.

**Последствия.** Правило записано в `.claude/rules/workflow.md` (Координация, п. 9) и действует во всех сессиях.

## D-013. Опоры игры
2026-10-15 · принято (решение Тима, задача 1.2)

**Контекст.** В GDD v0.1 опоры смешивали ощущения игрока и технические условия (данные в YAML, seed). По техническим пунктам нельзя решать спорные вопросы дизайна.

**Решение.** Пять опор игры (GDD §2): история из системы, не из сценария; хрупкий взлёт; последствия живут дольше героя; мир живёт без игрока; хроника — главный результат. «Данные, а не код» и «воспроизводимость» вынесены в подраздел «Принципы разработки»; они по-прежнему действуют (D-002, D-003).

**Последствия.** Спорная идея проверяется по опорам: противоречит опоре — меняется идея. Новая опора или правка старой — новой записью в DECISIONS.

## D-014. Темп игры
2026-10-15 · принято (решение Тима, задача 1.2); уточнено D-168

**Решение.** Решение игрока — раз в 1–2 минуты игры. Действия длятся от недель до месяцев, за действие 2–4 события с выбором. За 10 минут проходит 1–3 года жизни героя.

**Последствия.** Это ориентир для длительностей действий, частоты событий и рассказчика (этапы 2–3) и для метрик прогона (2.7): среднее число событий с выбором на год жизни.

## D-015. Амбиции главы рода и слава рода
2026-10-15 · принято (решение Тима, задача 1.2)

**Контекст.** Победы нет (D-016), но игроку нужна цель на жизнь героя и причина играть за следующее поколение.

**Решение.**
- Игра предлагает 2–3 амбиции по текущему положению героя (роль, долги, враги, покровители). Игрок выбирает одну и может сменить. Амбиции — контент, роль добавляет свои (у авантюриста — «осесть»).
- Слава рода копится поколениями из подвигов и позора глав и влияет на доступ к дворам, покровителям, бракам. Это сверх наследства, которое реально остаётся в мире.

**Последствия.** Нужны системы амбиций и славы рода; этап и формат определит architect при планировании этапов 3–4 и 6. Достигнутые и проваленные амбиции попадают в хронику.

## D-016. Конец игры и сохранения
2026-10-15 · принято (решение Тима, задача 1.2); уточнено D-058

**Решение.**
- Победы и оценки нет. Партия кончается, когда род пресёкся (наследника нет) или игрок сам её завершил. Предела по времени нет.
- В игре одно автосохранение, без ручных сохранений и откатов: решения и случайности окончательны.
- В конце игрок видит полную хронику и итог рода: годы и поколения, главы рода, достигнутые и проваленные амбиции, слава, вершина и дно рода.

**Последствия.** Сохранение и загрузка из файла и по seed (D-003) остаются инструментом разработки и прогонов, игроку они не показываются. В задаче 2.8 интерфейс делает автосохранение после каждой команды игрока, включая выбор в событии, а не кнопки «сохранить/загрузить»: иначе перезагрузка страницы даст переиграть выбор. Временный наследник (D-007) пока не даёт роду пресечься; пресечение появится на этапе 4.

## D-017. Падение не кончает игру
2026-10-15 · принято (решение Тима, задача 1.2); уточнено D-053, D-165

**Решение.** Разорение, тюрьма, опала, увечье — не конец партии, а новое положение героя со своими действиями и событиями (бегство, долговая тюрьма, служба за гроши), из которого можно выбраться. Партию кончает только пресечение рода или выход игрока (D-016).

**Последствия.** Контент должен покрывать «дно»: у положений падения есть доступные действия и пути наверх. Состояние героя без доступных действий — ошибка, которую стоит ловить инвариантом, когда появятся условия доступности (2.2).

## D-018. Игрок готовит наследника заранее
2026-10-15 · принято (решение Тима, задача 1.2)

**Решение.** Наследник виден игроку при жизни героя. Воспитание, брак, завещание влияют на следующую жизнь.

**Последствия.** Полностью — на этапе 4 вместе с браками и детьми (D-010). До того действует временный наследник (D-007).

## D-019. Хроника: только знаковые события, включая мировые
2026-10-15 · принято (решение Тима, задача 1.3); уточнено D-040, D-057

**Контекст.** Первый вариант образца был слишком подробным: хронику целой жизни, а тем более нескольких поколений, никто не станет читать (опора 5, D-013).

**Решение.**
- В хронику попадают только знаковые события: жизнь героя (рождение, брак, смерть, тяжёлые раны, смена положения), крупные деньги и долги, начало и конец отношений, события мира и решения игрока, запустившие цепочку. Повседневное в хронику не идёт.
- События мира (война и мир, смерть правителей, кризисы) записываются наравне с жизнью героя, если они задели героя или регион. Они не зависят от выбора игрока (опора 4).
- Ориентир: 25–45 строк на жизнь героя, около одной строки в год. Правила отбора и значимости уточняются в 2.6.
- Решение игрока, запустившее цепочку, помечается в хронике.

**Последствия.** Нужна оценка значимости записи и фильтр в хронике (2.6). Образец — `docs/samples/chronicle-target.md`.

## D-020. Сущности с постоянными id и ссылки в хронике
2026-10-15 · принято (решение Тима, задача 1.3); уточнено D-040, D-051, D-057

**Решение.** Каждая сущность (персонаж, место, держава, организация, долг, договор, событие) получает постоянный id. Записи хроники хранят id сущностей, а не готовый текст. В интерфейсе имена в хронике — ссылки на страницы сущностей, которые строятся из состояния игры и записей хроники.

**Последствия.** Требование к состоянию (2.1) и хронике (2.6); страницы и ссылки — в интерфейсе (2.8; с D-051 — 2.10). Сущности вне окружения героя остаются в состоянии в грубом виде и раскрываются при приближении (GDD §12).

## D-023. Державы региона
2026-10-15 · принято (решение Тима, задача 1.6); уточнено D-026

**Контекст.** GDD §6 задавал четыре прототипа без названий и деталей. Авантюристу нужны разные дворы и разные способы подняться, а хронике — конфликты между державами.

**Решение.**
- Четыре большие державы: Free Provinces of Haverland (морская торговая республика), Kingdom of Aurenne (абсолютистская монархия), Borean Empire (реформируемая восточная империя), Sultanate of Izmara (многонациональный султанат). Устройство, столицы и чем интересна каждая — GDD §6.
- Плюс 2–3 малые державы (вольный город, княжество, степная орда) как буферы и «серые зоны». Их названия и места определит карта.
- Названия держав и столиц — наши, на английском. Остальные названия (города, провинции, малые державы) — из Azgaar, Тим правит их под культуру своей державы. Культуры имён: Haverland — German, Aurenne — French, Borea — Ruthenian, Izmara — Turkish с общинами Greek и Levantine, малые — Italian, Hungarian, Mongolian.

**Последствия.** Этап 5 заводит державы как контент с id `haverland`, `aurenne`, `borea`, `izmara`. Роли и события опираются на устройство держав (векселя Хаверланда, патенты Оренна, Табель Бореи, откупа Измары) — это ориентир для content-writer и этапа 6.

## D-024. Регион и настройки Azgaar
2026-10-15 · принято (решение Тима, задача 1.6); уточнено D-026

**Контекст.** D-009 задал масштаб: 40–60 провинций, 15–25 городов, побережье и внутреннее море. Azgaar строит провинции вокруг бургов (поселений): число провинций — доля от числа бургов (Provinces ratio), поэтому городов мало, а бургов нужно много.

**Решение.**
- Раскладка: на западе океан, из него узкий пролив во внутреннее море. Хаверланд — северо-западное побережье океана у входа в пролив; Оренн — запад и юго-запад суши; Борея — север и северо-восток с недавним выходом к морю; Измара — южный и восточный берега моря и пролив.
- Настройки генератора (Azgaar 1.154): шаблон высот Mediterranean, 10K точек, размер карты 1600 × 900 px, 1 px = 1.25 км (регион около 2000 × 1100 км), набор культур European, 8 культур, 7 держав (4 большие и 3 малые), около 120 бургов, Provinces ratio 40, Size variety 4, Growth rate 1.5, 4 религии. Пошагово — `docs/map-guide.md`.
- Город в игре — бург групп `capital` и `city` (столицы и крупнейшие бурги). Остальные центры провинций — городки. Нужное число городов (15–25) Тим добирает, переводя бурги между группами.

**Последствия.** Если после правок провинций или городов окажется вне D-009, Тим перегенерирует провинции (Tools → Regenerate → Provinces) или меняет группы бургов. Настройки нужны один раз: дальше карта правится вручную, а не генерируется заново.

## D-025. Хранение и импорт карты
2026-10-15 · принято (решение Тима, задача 1.6)

**Контекст.** Карту делает и правит Тим в Azgaar, а игре нужны данные по D-002: YAML со схемой, целые числа, проверка валидатором. Картинки карты в игре нет (GDD §15).

**Решение.**
- **Исходники** лежат в `map/` в корне репозитория, не в `content/` (туда попадает только YAML контента):
  - `map/region.map` — сохранение Azgaar (Save → machine). Единственный источник правок: Тим открывает его через Load, правит и сохраняет заново;
  - `map/region.json` — Export → JSON → full из того же состояния карты. Источник импорта;
  - `map/region.svg` — картинка карты для людей (Export → .svg). В игру не идёт.

  Три файла обновляются вместе, одним коммитом. Версия Azgaar берётся из `info.version` экспорта.
- **Что берём из экспорта:**
  - державы (`pack.states`, без 0 — Neutrals): имя, форма правления, столица, соседи;
  - провинции (`pack.provinces` и `cells.province`): имя, держава, центр, соседи по смежности клеток, площадь, население, преобладающие рельеф, культура и вера, выход к морю и морская зона. Мелкие ничейные клочки суши импорт присоединяет к соседней провинции; «серые зоны» дают малые державы (D-023);
  - города (`pack.burgs`): все бурги групп `capital` и `city` плюс центры провинций как городки. Поля: имя, провинция, держава, население, порт, столица, стены, цитадель. Остальные бурги не берём;
  - дороги (`pack.routes`): группы `roads` и `trails` дают тип связи между соседними провинциями (дорога, тропа или бездорожье) и её длину; `searoutes` — морские пути между портами;
  - моря: морские зоны (3–6) Тим размечает зонами Azgaar по воде (Tools → Zones), потому что Azgaar считает весь связный океан одним объектом. Береговые провинции и порты относятся к зоне, соседство зон — по клеткам.
- **Не берём:** клетки и их геометрию (нужны только при расчёте), высоты, климат, реки, гербы, цвета, армии, рынки.
- **Как это станет контентом (этап 5):** инструмент `tools/import-map.ts` (Node, вне ядра) читает `map/region.json` и пишет `content/world/map.yaml` с пометкой «сгенерировано, не править руками». Ядро получает его как обычный контент: схема в `schema.ts`, перекрёстные ссылки в `load.ts`. Числа целые (D-003): население, площадь, координаты центров в км (только для расстояний), длины путей; дни пути считаются по скоростям из `settings`. Один и тот же экспорт даёт один и тот же YAML байт в байт.
- **id** — `lower_snake_case` от английского имени (`ostmere`, `aurenne`), при совпадении — с суффиксом. Числовой id из Azgaar хранится полем `azgaarId` для сверки при повторном импорте. Переименование в Azgaar меняет id; битые ссылки контента покажет валидатор.
- **Игровые добавки** (описания, теги, особые правила провинций и городов) лежат в отдельных файлах `content/world/*.yaml` со ссылками на id. Импорт их не трогает.

**Последствия.** Этап 5 добавляет в контент ключи мира и расширяет правило «каждый файл — `settings`, `names`, `actions`, `events`». Детали схемы и скоростей пути определит architect при планировании этапа 5; это решение задаёт только состав данных и порядок работы. Правка карты = правка `region.map` в Azgaar + новый экспорт + повторный импорт.

## D-026. Карта региона: seed 343
2026-10-15 · принято (решение Тима, задача 1.6)

**Контекст.** Тим попросил сгенерировать и выбрать карту за него. Сайт Azgaar из облачной сессии недоступен, поэтому карта сделана в локальной копии Azgaar 1.154.1 (исходники с GitHub), в браузере Chromium под управлением скрипта. Шаблон Mediterranean всегда даёт замкнутое море: у западного края стоят горы.

**Решение.**
- Карта — seed 343, Тим выбрал её из двух лучших примерно из 180 сгенерированных. Источник правды — `map/region.map`; JSON и SVG экспортированы из того же состояния. Скрипты, которыми сделаны правки, лежат в `map/scripts/` (что делает каждый — `map/README.md`).
- Для пролива на запад в локальной копии ослаблены западные горы шаблона Mediterranean (`Hill 2-3 12-25 0-5 20-80` вместо `30-70`). Файл `.map` при этом обычный, его открывает сайт Azgaar.
- Настройки отличаются от D-024: Provinces ratio 26 вместо 40 (при 40 выходило 70–80 провинций), население — `1 population point = 500`, `Urbanization rate = 4`. Итого около 34 млн жителей; столицы больших держав — 120–220 тыс., кроме новой Novomor (35 тыс.); Kostrograd — 90 тыс.
- Раскладка по факту (отличается от схемы D-024):
  - Хаверланд — северо-запад и северный берег пролива;
  - Измара — юг моря и весь южный берег пролива;
  - Оренн — север, внутренние земли с узкой полосой берега без портов;
  - Борея — восток и юго-восток, самая большая держава (19 из 54 провинций). Новая столица Novomor — морской порт, старая Kostrograd на дальнем севере.
- Малые державы: Duchy of Ticumiegia (Italian), Byblian Despotate (Greek), Principality of Duhadia (Hungarian). Отличия от D-023: степной орды нет, греческие имена ушли к Byblia, у Измары одна община — Levantine.
- Ничейной суши нет: её присоединили к соседям. Имена бургов, провинций и Duhadia пересозданы по культурам; державы и столицы названы по D-023.
- Провинции: 54, у каждой есть центр-бург (где Azgaar его не поставил, бург добавлен); провинции меньше 8 клеток слиты с соседними. Несколько провинций включают острова (у измарской Onauernia — остров в 64 клетки, по суше касающийся только мыса Бореи), у Бореи остались 3 мелких анклава (2–9 клеток) внутри Измары.
- Дороги, тропы и морские пути перестроены после всех правок бургов: каждая портовая столица — конец морского пути, через каждый порт идёт морской путь, бургов вне дорог нет. Городки на островах вне материка сделаны портами. После перестройки Azgaar дал 8 дорог, 104 тропы и 34 морских пути, поэтому большая часть связей между провинциями при импорте выйдет тропами.
- Города: 20 бургов групп `capital` и `city` — по 3 у Хаверланда и Оренна, по 5 у Бореи и Измары, 2 у Byblia, по 1 у Ticumiegia и Duhadia.

**Дополнения к D-025 (вводные для импорта на этапе 5).**
- Морские зоны размечены скриптом, а не вручную. Морская зона — любая зона типа `Sea`; другие зоны Azgaar удалены. Четыре зоны главного моря связны: Western Ocean, The Strait, Inner Sea (west), Inner Sea (east). Пятая, Northern Sea, — три залива у северного края карты, которые соединяются за её пределами; её куски несвязны, это нормально.
- Из 38 портов 13 — речные или озёрные: Azgaar 1.154 пускает морские пути по судоходным рекам. Такой порт относится к морской зоне по своему морскому пути, а не по соседним клеткам. Столицы Ostmere, Novomor и Sarayhan стоят прямо на берегу главного моря.

**Последствия.** GDD §5–§6 описывают эту карту. Правки карты — в `region.map` (`docs/map-guide.md`); перегенерировать её не нужно.

## D-030. Копилка идей

**Решение.** Идеи Тима по игре, даже мелкие, хранятся в `docs/IDEAS.md` со статусами (новая, обсуждена, взята, отложена, отклонена) и номерами `I-001…`. Обсуждаются в постоянной сессии «Идеи». ## D-031. Шесть характеристик персонажа

**Решение.** У персонажа шесть характеристик, как в CK3: Дипломатия, Военное дело, Хозяйство, Интриги, Учёность, Доблесть (Diplomacy, Martial, Stewardship, Intrigue, Learning, Prowess). ## D-032. Черты: без лимита, с противоположностями; образование — черта
2026-10-15 · принято (решение Тима, задача 1.4)

**Решение.**
- Число черт не ограничено, но противоречащие черты одновременно невозможны; у многих черт есть противоположность, и получение одной снимает другую. Набор берётся из CK3 и подгоняется под 1700 год.
- Категории: характер, образование, умения, тело (врождённое и увечья), репутация, тайны.
- Характер складывается к взрослости (2–3 черты) и меняется только событиями-потрясениями. Репутация появляется от публичных поступков и уходит по сроку или условию.
- Образование — черта по одной из пяти характеристик (кроме Доблести), одно на жизнь, уровень 1–4, надбавка +2/+4/+6/+8 к своей характеристике.

**Последствия.** Черты — контент в YAML (категория, противоположность, влияние, заметность). Схема и загрузчик проверяют, что противоположности симметричны. Код — 2.3.

## D-033. Здоровье — состояния со стадиями
2026-10-15 · принято (решение Тима, задача 1.4); уточнено D-051, D-164

**Решение.** Здоровье — набор состояний (раны, болезни, немощь) со стадиями и переходами, а не общая шкала. Рана может зажить, загноиться, дать лихорадку, оставить шрам, увечье или «старую рану», которая изредка открывается. Смертность — таблица по возрасту × множители состояний. У каждой смерти есть причина, она идёт в хронику.

**Последствия.** Шкала здоровья 0–100 из каркаса заменяется в задаче 2.3 (с D-051 — 2.9). Шансы переходов — целые дроби. Роды — этап 4, эпидемии — этап 5.

## D-034. Пол и исторические ограничения

**Решение.** Мир живёт по нравам 1700 года: часть путей закрыта по полу (офицерский патент, служба в армии), у женщин есть свои пути (вести дела вдовой, салон, покровительство через двор). Женщина может быть главой рода и героем игрока, тупиков у неё нет (D-017). Ограничения — условия действий и событий в контенте, а не правило ядра.

## D-035. Мнения: затухание по причине и характеру
2026-10-15 · принято (решение Тима, задача 1.4)

**Решение.** Мнение — целое от −100 до 100, сумма причин. У причины своё правило: затухает за срок, держится до условия или не затухает никогда. Черты меняют память (мстительный не забывает обид, отходчивый забывает быстрее). Причину может снять событие. Причину вида «убил моего отца» получают наследники убитого к убийце. Вражда предка переходит наследнику героя ослабленной причиной «враг отца»; устойчивое соперничество по наследству — отношение (D-036). Игрок видит мнение словами и причинами, число — по наведению.

**Последствия.** Код — 2.4. Наследование вражды полностью — этап 4.

## D-036. Отношения создаёт событие; долг — сущность
2026-10-15 · принято (задача 1.4)

**Решение.** Отношения: друг, соперник, покровитель ↔ протеже, любовник; родство — на этапе 4. Связь создаёт и рвёт событие, а не порог мнения. Соперничество может переходить по наследству. Должник и кредитор — не отношение, а следствие открытого долга, который является сущностью (D-020). Служба — должность, а не личная связь.

**Последствия.** Из списка отношений задачи 2.4 убран «должник». Долги — этап 6.

## D-037. Видимость: известность, заметность черт, знакомство, тайны
2026-10-15 · принято (решение Тима, задача 1.4); уточнено D-051

**Контекст.** Тим: баланс между «всё открыто» и «только со знакомством»; на страницу известного человека, например короля, можно зайти, ни разу его не видев.

**Решение.**
- Своего героя игрок видит полностью.
- У человека есть известность (частное лицо, местная фигура, известен в державе, известен всем); от неё зависит, что о нём знают понаслышке.
- У черты есть заметность: явная (видна сразу), обычная (со знакомством или понаслышке у известных), тайная (только через интриги и события).
- Знакомство героя: не знаком → знаком → близок; с ним открываются характер, умения, мнение о герое и его причины.
- У тайны есть список знающих; раскрытая тайна может стать репутацией.

**Последствия.** Состояние хранит, кто что знает (2.4); страницы сущностей (D-020, 2.8; с D-051 — 2.10) показывают только известное игроку.

## D-038. Предыстория первого героя
2026-10-15 · принято (решение Тима, задача 1.4); уточнено D-055, D-167

**Контекст.** Тим не хочет ни случайных характеристик на старте, ни ручной настройки. Референс — настройка героя в Mount & Blade, но без её сюжетной линии.

**Решение.**
- Перед игрой — 4–6 сцен о рождении, семье, детстве, юности и образовании. Это обычные события из общего набора, выбранные по условиям и случаю; у разных партий разные предыстории.
- Ответы дают характеристики, черты, образование, умения, деньги и снаряжение; ответ задаёт направление, точное значение — случай.
- Ответ может оставить след в мире (человека, связь, долг, вещь), но обязательного набора нет. Заданного начала и главной линии нет.
- Игра начинается в 16–21 год, около 1700 года; первые строки хроники — из предыстории.
- Наследники опроса не проходят: их детство прожито в игре (D-018).

**Последствия.** Предыстория строится на движке событий (этап 3); сцены авантюриста — контент этапа 6. До того герой каркаса создаётся как сейчас.

## D-040. Формат события (storylet)
2026-10-15 · принято (решение Тима, задача 1.5); уточняет D-019, D-020; уточнено D-057, D-161

**Контекст.** GDD §9 перечислял части события без подробностей. Формат должен позволять всё, что есть в образце хроники и модели персонажа (§8), и ничего лишнего.

**Решение.**
- Событие — запись в контенте: id, тяжесть (лёгкое, среднее, тяжёлое), вес с модификаторами-дробями, условия, роли, текст, варианты, страницы, последствия, продолжения, строка хроники. Подробно — GDD §9.1.
- Условия: действие, место, время года, характеристики, черты, здоровье, деньги, вещи, должность, положение героя или участника, отношения и мнения через роли, знание героя. Условия видят правду мира.
- Последствия: деньги, вещи, раны и болезни, черты и репутация, тайны и знающие, мнения с причиной и затуханием, отношения (создать, разорвать, передать по наследству), долг как сущность (D-036), должность, положение, контракт, переезд, смерть с причиной, продолжения.
- Событие может состоять из нескольких страниц-сцен.
- Строку хроники даёт вариант или исход; строки страниц одного события склеиваются в одну запись. Ссылками остаются все сущности D-020 (люди, места, державы, организации, долги, договоры, события); суммы, выбранные формулировки и отображаемые имена сущностей фиксируются в момент записи, чтобы запись через годы читалась так же.
- Значок ▸ (D-019) ставится автоматически, если выбор игрока открыл продолжение или историю, создал или разорвал отношение, открыл или закрыл долг, заключил контракт, получил или потерял должность, вступил в брак, взял или сменил амбицию, сменил положение. Автор события может пометить вариант вручную. Так воспроизводятся все ▸ образца хроники. Отбор значимости — 2.6.
- Вес после множителей округляется вниз; итог 0 — событие невозможно.
- Сцены предыстории (D-038) и события мира (этап 5) — в том же формате.

**Последствия.** Этап 3 делает схему по этому формату; нынешние поля `weight`, `actions`, `text`, `options` из каркаса становятся её частью. Примеры — `docs/samples/storylets.yaml`, это черновик, а не контент: точные имена полей определит architect на этапе 3.

## D-041. Роли заполняются живыми людьми
2026-10-15 · принято (решение Тима, задача 1.5; уточняет GDD §9); уточнено D-056, D-160, D-161

**Решение.**
- Роль заполняется человеком, который уже живёт в мире: работодатель, служит рядом, знакомый, по отношению, по должности, проездом, переданный продолжением. Под событие людей не создают.
- У роли условия на человека и предпочтения (множители при выборе из подходящих). Обязательную роль некем заполнить — события нет. Необязательная роль может остаться пустой, текст это учитывает.
- Безымянные массовки (разбойники, толпа) ролями не считаются.
- Участники события становятся знакомыми героя (D-037).

**Последствия.** Событиям нужно население вокруг героя (2.5) с должностями и местами службы; без него часть событий не будет случаться — это нормально, а частоту покажут метрики прогона (2.7).

## D-042. Проверки характеристик
2026-10-15 · принято (решение Тима, задача 1.5; уточняет D-031)

**Решение.**
- Проверка — характеристика против сложности или встречная, против характеристики другого участника. Шанс — 50% + 5% за очко разницы, в пределах 5–95%; черты и умения дают надбавки к характеристике в проверке. Всё в целых числах (D-003).
- Игрок видит шанс до выбора словами: почти безнадёжно, рискованно, как повезёт, вероятно, почти наверняка. Процент — по наведению (как характеристики, D-031).

**Последствия.** Формула — отправная точка баланса; менять её можно по метрикам прогонов отдельным решением.

## D-043. Недоступные варианты видны серым с причиной
2026-10-15 · принято (решение Тима, задача 1.5)

**Решение.** Вариант, условия которого не выполнены, показывается серым с причиной («Requires 40 crowns»), как в CK3. Если причина выдала бы то, чего герой не знает (тайну, скрытую черту, чужое мнение), вариант скрыт совсем.

**Последствия.** Причину интерфейс строит из условий варианта; тексты причин — в контенте (D-002). Задача этапа 3 и интерфейса (2.8).

## D-044. Продолжения: расписание, крючки, истории со сроком
2026-10-15 · принято (решение Тима, задача 1.5); уточнено D-051, D-053, D-161

**Решение.**
- **По расписанию:** вариант назначает событие через N дней с теми же участниками. Событие может быть «только продолжением» и не входить в общую колоду.
- **Крючки:** отношения, долги, тайны, обязательства, должности сами делают возможными другие события, без жёсткой цепочки. Долгие истории вроде Торна (1700 → 1721) получаются так.
- **История:** открытая линия со сроком и приоритетом. Если к сроку развязки нет, срабатывает запасная развязка: тихая (без строки хроники) или явная, если сюжет требует.
- **Выбывший участник:** назначенное событие, обязательную роль которого некем заполнить, отменяется. Запасная развязка — событие с условиями; если ни одна не подходит, история закрывается молча. Со смертью главного участника его назначенные события и истории отменяются; со смертью героя то, что наследуется (долги, вражда, обязательства), остаётся крючками (этап 4).

**Последствия.** Состояние хранит назначенные события и открытые истории (2.1, этап 3; с D-051, D-053 — очередь назначенного в 2.2, истории на этапе 3). Сохранение посреди истории продолжает её же.

## D-045. Рассказчик: темп и выход со дна
2026-10-15 · принято (решение Тима, задача 1.5); уточнено D-160, D-165, D-168

**Решение.**
- Рассказчик держит темп D-014: 2–4 события с выбором за действие, минимальный промежуток между событиями.
- Чередует тяжёлое и лёгкое через напряжение: тяжёлые события его поднимают, со временем оно спадает; при высоком напряжении тяжёлые не выпадают.
- Порядок выбора: продолжения на сегодня → события открытых историй (вес растёт к сроку) → общая колода.
- На дне (D-017) поднимает вес событий «путь наверх» и при долгом их отсутствии даёт одно вне очереди.
- Удачу героя не корректирует: успех не наказывается, опасность идёт от мира (опоры 1, 2).
- Перерыв перед повтором события; пометки «раз за жизнь» и «раз за партию».
- Событие без выбора останавливает время («Дальше»), только если пишет строку хроники; остальное идёт в журнал.

**Последствия.** Параметры темпа — в `settings` контента. Метрики прогона (2.7) показывают число событий с выбором на действие и на год.

## D-046. Тексты: второе лицо и своя мини-грамматика
2026-10-15 · принято (решение Тима, задача 1.5); уточнено D-055, D-162, D-163

**Контекст.** GDD §14 оставлял выбор: Tracery или аналог. Библиотека Tracery берёт случайность из `Math.random` и глобального состояния, что запрещено в ядре (D-003), а валидатор не может проверить её правила.

**Решение.**
- Текст события — во втором лице («You…»). Хроника — в третьем лице, строки биографии без подлежащего.
- Своя мини-грамматика в духе Tracery внутри ядра: символы `#name#`, общие и свои у события, у формулировки может быть условие. Подстановки ролей, местоимений по полу и видимых полей — `{role}`, `{role.he}`.
- Формулировку выбирает генератор, засеянный seed партии и номером события. Мировой поток не тратится: правка текстов не меняет историю, а одна партия всегда читается одинаково.
- Валидатор проверяет символы, циклы, роли и поля.
- Модификатор заглавной буквы для начала предложения (как `.capitalize` в Tracery): `#dawn.capitalize#`, `{recruiter.He}`. Точный синтаксис — этап 3.
- В YAML `#` после пробела начинает комментарий, поэтому текст с символами грамматики пишется в кавычках или блоком `>-`. Architect на этапе 3 может выбрать другой разделитель, если этот окажется ненадёжным.

**Последствия.** Плейсхолдер `{name}` каркаса заменяется ролями на этапе 3. Местоимения появляются с полом (2.3, D-010).

## D-047. Люди рядом с героем живут по тем же событиям
2026-10-15 · принято (решение Тима, задача 1.5); уточнено D-056, D-161, D-166, D-174

**Решение.** Событие может быть для героя, для людей мира рядом с героем или для обоих. У события есть главный участник (`protagonist`) — тот, чьё это событие: условия, проверки (его характеристикой), последствия и строки хроники пишутся от его лица. Человек мира выбирает вариант по весам с поправками по чертам; текст ему не нужен, последствия те же, строка идёт на его страницу и в хронику по общим правилам.
- **Герой не попадает в роли событий людей мира.** Всё, что затрагивает героя, решается только через его выбор (опора 2: решения окончательны, но это решения игрока). Если человек мира действует против героя (обвиняет, вызывает, требует долг), это пишется как событие героя, где этот человек — роль, а его инициатива — вес по его чертам (пример — `rival_accuses_at_court`). Люди вдали от героя живут по грубым правилам 2.5 (GDD §12).

**Последствия.** У вариантов таких событий есть веса выбора для людей мира. Стоимость прогона на 300 лет нужно держать под контролем: «рядом» определяет 2.5, метрики — 2.7.

## D-050. Соавторство, а не исполнение
2026-10-15 · принято (решение Тима)

**Контекст.** Агенты выполняли любое сообщение Тима как поручение, даже мысль вслух или сомнение. Такие правки ломали уже обсуждённое, проверенное и отлаженное, и в решениях начинался хаос. Тиму нужен соавтор: диалог, свои предложения, честные возражения.

**Решение.** В `.claude/rules/workflow.md` раздел «Соавторство»:
- раздел касается реплик Тима; задача из утверждённого плана и промпт по ней — уже поручение;
- по умолчанию сообщение Тима — обсуждение; правки только после явного «сделай / меняй / берём» или выбора варианта; записать идею в IDEAS.md или вопрос в STATUS можно и по реплике-мысли;
- агент высказывает своё мнение и предлагает решения лучше; рекомендуемый вариант — его настоящее мнение; одно возражение, без споров по кругу;
- прежде чем трогать принятое, агент называет, что сломается и что придётся перепроверить;
- если Тим настаивает на изменении принятого, а агент против, и правка меняет запись DECISIONS или требует заново проверять влитую работу, — сначала независимое второе мнение architect, потом окончательное слово Тима; возражение и мнение architect записываются в DECISIONS; остальные споры решает Тим без второго мнения;
- реплика посреди задачи не меняет план без обсуждения.

**Последствия.** Изменения принятого идут медленнее, зато осознанно. В инструкции architect добавлен раздел «Второе мнение», в чек-лист reviewer — проверка, что принятое не изменено без явного решения Тима. Уже идущие сессии правило не видят: правила грузятся при старте сессии. Номер D-050 взят, пока шла задача 1.5 (ей отводились D-040…D-049, заняты D-040…D-047); D-039, D-048 и D-049 свободны.

## D-051. Разбивка этапа 2
2026-10-15 · принято (решение Тима, задача 2.0); уточняет D-020, D-033, D-037, D-044

**Контекст.** Предварительная разбивка 2.1–2.8 писалась до решений 1.4–1.6. Задача 2.3 в ней слишком крупная (характеристики, черты, пол, здоровье, смертность), 2.8 совмещает интерфейс и страницы сущностей, а ядро этапа 1 лежит в нескольких общих файлах, которые правила бы каждая задача.

**Решение.**
- 2.1 — не «состояние и сохранения», а разрезание ядра на модули с точками подключения (D-052); поведение игры не меняется.
- Здоровье и смертность выделены из 2.3 в новую задачу 2.9 (D-033 называл задачу 2.3). Страницы людей и ссылки выделены из 2.8 в 2.10.
- Версия формата сохранения переезжает из 2.1 в 2.8: пока нет автосохранения, сохранённых партий нет.
- Очередь назначенного (D-044) — в 2.2, открытые истории со сроком — на этапе 3 вместе с движком: их формат без движка не определить.
- Модель мнений и отношений (2.4) делается на этапе 2, хотя потребителя — событий с ролями — ещё нет. Тим выбрал этот вариант против переноса 2.4 на этап 3. Поэтому цель этапа звучит «люди знакомятся», а не «связаны отношениями»: дружбы и соперничества из событий появятся на этапе 3.
- Номера старой разбивки сохранены, план и волны — в ROADMAP.

**Последствия.** Десять задач (плюс сам план 2.0) в пять волн, не больше трёх параллельно. У каждой задачи свой диапазон номеров решений (ROADMAP).

## D-052. Модули ядра и владение файлами
2026-10-15 · принято (решение Тима, задача 2.0); уточняет D-002

**Контекст.** Чтобы задачи этапа шли параллельно, они не должны править одни и те же файлы кода.

**Решение.**
- `src/core` делится на модули-папки (`character/`, `health/`, `time/`, `actions/`, `conditions/`, `events/`, `world/`, `relations/`, `chronicle/`, `save/`, `text/` и другие по плану). Модуль правит только свою папку, свой контент и свои тесты.
- Сборочные файлы (`game.ts`, `state.ts`, `lifecycle.ts`, `invariants.ts`, `effects.ts`, реестр условий, `content/schema.ts`, `content/load.ts`) собирают из модулей состояние, хуки персонажа и смерти, фазы дня, ключи эффектов и условий, ключи контента, перекрёстные проверки и инварианты. Их создаёт 2.1, дальше они правятся только между волнами через architect.
- Набор верхних ключей контента расширяется: у модуля свой ключ, а не только `settings`, `names`, `actions`, `events` (D-025 такое расширение уже предусматривал для мира).

**Последствия.** Правило владения файлами записывается в CLAUDE.md в 2.1. Не хватает точки подключения — сессия останавливается и описывает проблему; сборочные файлы правит ведущая сессия этапа с architect отдельным PR `[2.1a] …` между волнами (ROADMAP).

## D-055. Пол и местоимения до ролей
2026-10-15 · принято (решение Тима, задача 2.0); уточняет D-010, D-046; уточнено D-162, D-167

## D-056. «Рядом с героем» без карты

## D-057. Запись хроники: ссылки и уровень с 2.1
2026-10-15 · принято (решение Тима, задача 2.0); уточняет D-019, D-020, D-040

**Решение.**
- С 2.1 запись хроники хранит части текста — строки и ссылки `{id, имя на момент записи}`, а не готовый текст. Модули пишут хронику только через одну функцию `log`.

## D-058. Сохранения до выпуска не переносятся
2026-10-15 · принято (решение Тима, задача 2.0); уточняет D-016; уточнено D-169

**Решение.** У формата сохранения есть версия. Пока игра не выпущена, автосохранение прежней версии не переносится: игра сообщает «сохранение от прежней версии» и начинает новую партию. Миграции обязательны с первого выпуска для игроков.

**Последствия.** Задачи, меняющие состояние, не пишут миграций; версию поднимает тот, кто меняет формат. Механизм — 2.8.

## D-060. Сборочные файлы и модули ядра в коде
2026-10-15 · принято (задача 2.1); уточняет D-052; уточнено D-164

**Решение.**

- Реестр условий назван `condition-keys.ts`, а не `conditions.ts`: рядом лежит папка модуля `conditions/`, и `./conditions` читался бы двусмысленно. Поправки к характеристикам — отдельный сборочный файл `modifiers.ts`.

Ключи эффектов модуля — в `<модуль>/effects.ts`; код, который зовёт `createCharacter`, `kill` или `applyEffects`, — в отдельном файле модуля. Тест архитектуры запрещает циклы импортов в ядре.

**Последствия.** Модули из плана этапа 2 подключаются без правки сборочных файлов. Новый модуль вне плана, новый вид хука или ещё один верхний ключ — правка сборочного файла, то есть PR `[2.1a] …` между волнами.

## D-061. Запись хроники и причина смерти в коде

## D-071. Назначенное и прерывание действия
2026-10-16 · принято (задача 2.2); уточняет D-053

**Решение.**
- `later: [{after_days, effects}]` — обычный ключ эффектов (в `effects` действия или варианта события, схему варианта менять не понадобилось). Вложенный `later` допустим. Эффекты ставятся в очередь `state.scheduled` для того же персонажа в момент применения и срабатывают в фазе «назначенное» дня `dueDay`, в порядке постановки. Смерть персонажа убирает его записи; инвариант это проверяет. Эффекты `later` действия применяются при его завершении, как и остальные.
- Фаза «назначенное» возвращает true, если действия героя больше нет (например, герой умер от эффекта), иначе цикл дня не остановился бы.
- `end_action: true | "шаблон"` только записывает запрос в `state.interruptRequest`: эффекты применяются и при ответе на событие, и при завершении действия, где останавливать цикл дня нельзя (`game.ts` сборочный). Запрос исполняет фаза «конец действия» того же или следующего дня: действие прерывается без эффектов, пишется строка журнала (`kind: interrupt`, `level: journal`; текст по умолчанию `time.texts.interrupted`).
- Если запрос приходит в последний день действия, действие прерывается без эффектов, а не завершается.
- `interruptAction(ctx, шаблон?)` — немедленное прерывание для модуля здоровья 2.9; после него фаза здоровья возвращает true.

**Последствия.** Без активного действия `interruptAction` ничего не делает. Этап 3 кладёт в `state.scheduled` назначенные события.

## D-100. Здоровье в коде: состояния, стадии, переходы
2026-10-16 · принято (задача 2.9); исполняет D-033; уточнено D-165

**Решение.**
- У персонажа список состояний `conditions: [{id, stage, start, since}]`, не больше одного каждого вида. Состояния и их стадии — в `content/health.yaml`: вид (`wound`, `disease`, `frailty`), причина смерти, `permanent` (никогда не проходит: старая рана, немощь), стадии и исходы заживления.
- У стадии: `minDays` (срок до первых бросков), `severe` (тяжёлая), штрафы к характеристикам (через `modifiers.ts`), множитель смертности, строка `text` и переходы `{to, per10k}` — в другую стадию, в `heal` или в `death`.
- Переходы бросаются раз в неделю (дни, кратные 7) одним броском на состояние: шансы идут по порядку, остаток до 10000 — без изменений. Переход к стадии раньше или в `heal` — «к выздоровлению», позже или в `death` — «к смерти»; покой и дорога умножают эти шансы на проценты из контента (`rest`, `road`: списки действий, `better`, `worse`). Шансы — целые (D-003).
- Строка стадии пишется только на пути к смерти: тяжёлая стадия — в хронику, остальное — в журнал (GDD §8.9). Исход заживления (ничего, шрам, увечье с потерей умения, старая рана) бросается по весам; строка с чертой или новым состоянием — в хронику, без них — в журнал.
- Новые состояния без события — `onsets`: шанс в неделю с возраста (лихорадка, чахотка, немощь после 60).
- Тяжёлая стадия у героя прерывает действие, если это не покой (`interruptAction`, проверка каждый день в фазе здоровья); смерть от стадии — в фазе здоровья, от таблицы — в фазе смерти.
- Лекарь и Учёность лечащего на шансы пока не влияют: лечащих людей нет до 2.5 и событий с ролями этапа 3.

**Последствия.** Шкала 0–100 и `startHealth` убраны. 2.8 показывает состояния (`conditionsText` в `health/course.ts`), 2.6 отбирает строки по видам `health`, `death`, `death_cause`.

## D-110. Окружение героя: состав, пополнение, переезды
2026-10-16 · принято (задача 2.5); исполняет D-056

**Решение.**
- `state.circle` — id живых людей окружения в порядке вступления; героя и мёртвых там нет. `detailedCharacters` отдаёт героя, затем окружение. Все остальные живые — «вдали».
- Размер задаёт `population.circle`: ниже `min` окружение пополняется новыми людьми (каждый день, в фазе мира), `max` — жёсткий предел. Новый человек создаётся через `createCharacter`; фамилия случайная из `names.surnames`, возраст из `population.newcomerAge`, занятие по весам среди подходящих по возрасту.
- Герой и наследник в окружение не входят; занятие у них `null`. Смерть человека убирает его из окружения сразу (хук смерти), пополнение — в фазе мира того же дня.
- Раз в год (1 января) каждый член окружения с шансом `driftPer10k` уходит «вдаль», живым.
- Переезд: когда герой завершает действие из `population.moves` (поле `action` — id действия из `actions`; `content/actions.yaml` не меняется), `leave` случайных людей уходят вдаль, затем приходят `arrive` человек (до `max`), в доле `arriveFromFarPer100` — живые дальние нужного возраста (кроме только что ушедших), иначе новые; строка журнала `move` о герое. Прерванное действие окружение не меняет, переезд за одно действие выполняется один раз (`lastMoveEndDay`). Для 2.4: если `relationsPhase` когда-нибудь остановит день раньше конца действия, это уже учтено.

**Последствия.** Роли этапа 3 берут людей из `detailedCharacters(state).slice(1)`. Пока `population` в контенте нет, окружения нет и всё работает как раньше.

## D-111. Люди вдали: годовой тик

Обрезка давно умерших остаётся запасным путём.

## D-120. Мнение считается от даты: причины, память черт, фон
2026-10-16 · принято (задача 2.4); исполняет D-035

**Решение.**
- Мнение «кто о ком» — не поле, а сумма на заданный день: записи причин `{reason, holder, target, day, value, end}` (`state.opinionReasons`), постоянный фон от черт обоих и постоянная причина активной связи. Ничего не пересчитывается ежедневно: значение — функция даты (`opinionValue(ctx, holder, target, day)`), итог зажат в −100…100.
- Каталог причин — `content/opinions.yaml`: `value`, `kind` (`harm` или `benefit`) и затухание: `fade` на `days` (линейно до нуля, целыми числами), `never`, `held` (держится, пока событие не закончит её по имени `until`, например `debt_repaid`; `endHeldReasons`). Одну причину снимает `removeOpinionReason`; снятая запись остаётся с датой `end`.
- Память черт хозяина мнения — `traitEffects` по id черт: `fade` (0 — не забывает, 200 — вдвое быстрее) и `scale` (вес причины в процентах), для `harm` и `benefit` отдельно, несколько черт перемножаются. Фон — правила «черта хозяина → черта другого → значение» с общим пределом `background.max`. Мнение словами — шкала `words` в контенте (семь слов, GDD §8.6).
- Та же причина, что ещё действует, не удваивается, а обновляется (новая дата и величина).
- Данные хранятся только там, где участвует герой или кто-то из окружения (`addOpinionReason`, `startRelation` бросают исключение иначе): это правило бюджета сохранения (D-063), не игровое. Событие с ролью «вдали» должно само решить, нужна ли запись.

**Последствия.** Событий с эффектами мнений в контенте этапа 2 нет (D-051): модель проверена тестами. Наследственная вражда (D-035, «убил моего отца», «враг отца») — этап 4: для неё хватит `addOpinionReason` для наследника.

## D-121. Отношения: связь не зависит от мнения, смерть закрывает
2026-10-16 · принято (задача 2.4); исполняет D-036

**Решение.** `state.relations`: `{id, kind, a, b, start, end, endReason}`; виды — в контенте (`friend`, `rival`, `patron`, `lover`), у вида `symmetric` и постоянная причина в мнении (`opinion.a` — что `a` думает о `b`, `opinion.b` — наоборот; у симметричных одинаково, это проверяет валидатор), а также какое знакомство даёт связь. В паре покровитель — протеже `a` — покровитель. Связь создаёт и рвёт событие (`startRelation`, `endRelation` с причиной); смерть закрывает все активные связи умершего с причиной `death` (хук смерти). Прекращённые хранятся. Инварианты: нет связи с собой, нет двух активных одного вида на одну пару (в любом порядке), обе стороны живы, `end` и `endReason` либо оба, либо ни одного. Строки хроники о начале и конце связей не пишутся: это решит этап 3 вместе с событиями (GDD §8.9) и 2.6.

## D-122. Знакомство героя: время рядом, один раз в неделю
2026-10-16 · принято (задача 2.4); исполняет D-037

**Решение.** `state.acquaintances`: `{holder, other, level, since, closeSince}`, уровни `known` и `close`, отсутствие записи — «не знаком»; хозяин — только герой (у наследника список свой, перенос знания — этап 4). Фаза связей (`relationsPhase`) раз в неделю (по номеру дня, один раз за день): с шансом `meetPer100` герой знакомится с одним случайным человеком окружения, которого не знает; с шансом `closePer100` один из знакомых дольше `closeAfterDays` и ещё живущих в окружении становится близким. Уровень никогда не понижается. Связь даёт не меньше знакомства, чем указано у её вида (друг, покровитель, любовник — близок; соперник — знаком), это считается из `relations`, без записи. Броски идут из собственного потока модуля (`state.relationsRng`, `seedRng(seed, 2)`, создаётся при первом использовании): мировой поток и остальная игра не меняются, хроника без мнений совпадает с прежней. ## D-140. Интерфейс остаётся на обычном DOM; автосохранение — одна ячейка localStorage
2026-10-16 · принято (задача 2.8); закрывает вопрос фреймворка из D-001, выполняет D-016, D-043, D-058

**Решение.**
- Фреймворк не берём: экран — герой, действия, событие, вкладки «Хроника» и «Журнал» (по `entry.level`) — собирается обычным DOM, зависимостей не прибавилось. Вернуться к вопросу стоит, когда 2.10 добавит страницы людей с маршрутами.
- Автосохранение — один ключ `dynasty-sim:save` в `localStorage`, запись после каждой команды (`apply`) и при старте новой партии. Всё обращение к `localStorage` — в `src/ui` (`storage.ts` не касается DOM и проверяется тестами с поддельным хранилищем; `browserStore` — в `main.ts`).
- `save/readSave` не бросает исключений: версия формата, отличная от `SAVE_VERSION`, даёт `old_version` до всякой другой проверки (D-058), любое другое нарушение — `corrupt`. В обоих случаях игра говорит об этом и начинает новую партию. Версию поднимает тот, кто меняет формат.
- Переполнение квоты и недоступное хранилище не роняют игру: над героем появляется предупреждение, что сохранение не удалось; прежнее сохранение остаётся. Партия продолжается в памяти.
- «Новая партия» — с подтверждением (`confirm`), стирает сохранение. Без `?seed` и с тем же seed игра продолжает сохранённую партию; `?seed=N` с другим seed заменяет её после подтверждения. Seed виден в строке под заголовком. Ссылки «restart» и «new seed» убраны: ручных откатов нет (D-016).
- Недоступное действие показывается серым с причинами из `actionAvailability` (D-043). У вариантов событий условий пока нет (этап 3): серых вариантов там нет.

**Последствия.** Сохранение ~2 МБ при квоте ~5 МБ: запас есть, но рост состояния нужно мерить (метрики 2.7). Две вкладки пишут в один ключ, побеждает последняя запись — ограничение принято. Если квота станет узким местом — сжатие или IndexedDB отдельной записью.

## D-130. Отбор хроники: правила и формат записи
2026-10-16 · принято (задача 2.6); уточняет D-019, D-057, D-063, D-064; уточнено D-166

**Решение.**
- Отбор делает `log` при записи; пороги — `content/chronicle.yaml` (`bigSum: {min, percent}`, `repeatDays`, `famousFame`). Без ключа `chronicle` в контенте действует уровень автора записи (тестовые фикстуры).
- Строка о человеке, который не герой и не в `state.circle`, не хранится (`log` возвращает `null`). Строка о члене окружения — журнал; смерть и её причина у известного (fame ≥ `famousFame`) — хроника (◆).
- Герой: конец действия и выбор варианта — хроника, только если сумма не меньше `min` и не меньше `percent`% денег героя до неё, либо вариант помечен `mark: true` (▸); иначе журнал, вид записи `action`/`event` остаётся (метрики 2.7). Остальное — уровень автора. Повтор той же строки о здоровье в хронике в течение `repeatDays` уходит в журнал.
- В запись добавлено необязательное поле `mark: true` (есть только у помеченных), чтобы markdown мог поставить ▸. Остальной формат записи не менялся.
- Markdown: разделы только у глав рода, «год · возраст на первую запись года», месяцы, ссылки на других глав, ◆ для строк не-глав. Журнал — `journal-seed<N>-<years>y.md` рядом с хроникой, все хранимые строки с днями.

**Последствия.** Поле `mark` необязательное, формат сохранения совместим со старым: `SAVE_VERSION` не поднимается (D-140). Настоящий контент 2.6 не размечает ▸ (границы задачи): метки появятся с событиями этапа 3. Пока в хронике героя мало строк (см. CHANGELOG) — оно собирается из смертей, тяжёлых состояний, смены главы и крупных сумм.

- **self** — текущий герой и прежние главы рода (у кого в хронике есть запись `start`/`succession`): всё, включая тайные черты, деньги и числа.

- **stranger** — имя, пол, возраст «около N» (округление до 5), явные черты (`visibility: obvious`). Известность открывает по шагам: 1 — занятие и точные годы жизни, 2 — обычные черты, 3 — причина смерти (D-037).
- Тайные черты не попадают на чужую страницу никогда; через страницу видны только тайны (`secrets`), которые знает герой, — вид тайны без подробностей.
- Союзники и соперники: все связи человека, прекращённые тоже; группа по знаку мнения, которое связь даёт самому человеку (минус — соперник), без нового поля в контенте. «(dead)» у умершего партнёра, «(ended год)» у разорванной. У незнакомца связей нет.
- Мнение показывается только там, где данные хранятся (герой и окружение, D-063). Мнение прежних глав не показывается.
- Строки на странице — записи о человеке, уже виденные игроком, последние 30 в каждом из двух видов: «Хроника» всем, «Журнал» только у self (план 2.10: два вида). Характеристики умершего считаются на день смерти; мнение умершего не показывается.
- Связи показываются все, любовные тоже; скрытие тайных связей — за этапом 3 (нужно поле у вида связи в чужом модуле). Характеристики включают бонусы тайных черт (как в CK3).

**Интерфейс.** Адрес `#/person/<id>` (кнопка «назад» работает), имена в хронике и журнале — ссылки, имя героя ведёт на его страницу. Тексты подписей страницы лежат в коде интерфейса и ядра страницы (в схему контента не добавлялись: границы задачи).

**Последствия.** Страницы не пишут в состояние, сохранение не затронуто. Названия `BACKGROUND_TEXT`/`TIES_TEXT` (постоянные части мнения) — временные, пока нет контента для них. Вопрос фреймворка (D-140) снят: маршрутов хватило на hash-адрес, фреймворк по-прежнему не нужен. Страницы мест, держав, событий и долгов — когда сущности появятся (этапы 4–6).

## D-162. Область ролей; `{name}` остаётся подлежащим строки
2026-10-16 · принято (решение Тима, задача 3.0); уточняет D-055, D-046

**Контекст.** D-055 обещал заменить `{name}`, `{he}` ролями и переписать шаблоны действий и событий. Но `{name}` стоит и в шаблонах черт, здоровья, переездов и настроек — это строки о своём субъекте, ролей в них нет.

**Решение.**
- Условия, эффекты и тексты получают область ролей (роль → человек). В событиях — `{role}`, `{role.he}`…; `{name}`, `{he}`… везде остаются плейсхолдерами подлежащего строки (в событии — главный участник). Переписываются только тексты 13 событий (3.12): второе лицо и роли. Шаблоны действий, черт, здоровья и настроек не трогаем.
- Строки биографии без подлежащего (GDD §14) делаются при показе, а не в контенте: строка пишется с `{name}` в начале, а в разделе своего главы и на его странице имя (и «was» сразу за ним) снимается и следующая буква становится заглавной (`ownLine`): «Aubrey was badly wounded…» → «Badly wounded…», как в образце. В журнале, где строки разных людей вперемешку, имя остаётся.

**Последствия.** Контент-автор всегда начинает `result` с `{name}`. Хроника главы читается как в образце без переписывания старых текстов.

## D-163. Разделитель грамматики `<symbol>`
2026-10-16 · принято (решение Тима, задача 3.0); уточняет D-046

**Контекст.** `#symbol#` в YAML без кавычек молча обрезает строку: всё после ` #` — комментарий. Валидатор такую ошибку не видит, текст просто становится короче.

**Решение.** Символ грамматики — `<symbol>`, с заглавной буквы первой формулировки — `<Symbol>` (как `{He}` у местоимений). `<` и `>` в середине строки YAML ничего не значат, а в начале строки `<` не индикатор. `.capitalize` не нужен.

## D-164. Смерть от события — запросом в фазу смерти
2026-10-16 · принято (решение Тима, задача 3.0); уточняет D-033, D-060, D-063; уточнено D-174

**Контекст.** Эффекты применяются из файлов, которые не могут импортировать `lifecycle.ts` (цикл импортов).

**Решение.** Эффект `kill: <cause>` кладёт запрос в `state.deathRequests`; ближайшая фаза смерти (после выбора в событии — следующего дня) первым делом исполняет запросы через `kill` (строка смерти и причины, смена главы у героя). Причины насилия — в `health.causes` с текстом. Запрос на уже умершего (например, от болезни в фазе здоровья того же дня) игнорируется.
- Решение Тима: у героя `kill` допустим только в исходе `failure` тяжёлого события (`severity: heavy`) без `next` — шанс игрок видит словами до выбора (опора 2 без внезапности), а обречённый герой не выбирает на следующей странице. Правило действует на любой путь к герою: `effects` события героя, `on: {hero: …}`, `later` внутри исхода, события `who: both` (главный участник может оказаться героем). У людей мира в событиях `who: npc` — в любом исходе. В сценах предыстории `kill` запрещён: у сцен нет действия, дни после выбора не идут, и смерть исполнилась бы только после первого действия обречённого героя. Проверяет валидатор (3.5; для `deck: backstory` — 3.11).

**Последствия.** Строка о гибели приходит на день позже строки события — в хронике это та же неделя. Смерть героя внутри выбора не прерывает `apply`. Медиану смерти главы (D-059, 45–55) меряют 3.12 и 3.13.

## D-171. Условия и эффекты с областью ролей
2026-10-16 · принято (задача 3.1); исполняет D-162

## D-172. Контракты 3.1 для волны 2: события, роли, тексты
2026-10-16 · принято (задача 3.1); уточняет план 3.1 в ROADMAP

**Решение (сигнатуры, которые задачи 3.2–3.4 наполняют, не меняя):**
- `events/`: `eventWeight(ctx, event, protagonist) → число` (0 — невозможно; сейчас — привязка к действию, заполнимость ролей, `weight`); `startEvent(ctx, event, protagonist, given = {}) → boolean` (false и ничего не меняет, если роль не заполнить). Ожидающее событие — `{eventId, protagonist, scope}`; варианты применяются к главному участнику с этой областью, строка — через `renderTemplate`. У схемы события уже есть поле `roles` (схема `RoleSchema`), тексты события проверяет `checkEventTemplate`, роли — `checkRoles`.
- `roles/`: `baseScope(hero, protagonist)`, `fillRoles(ctx, roles, base) → Scope | null`, `canFillRoles` — по порядку объявления, первый подходящий из окружения без случайности; `circle` — окружение, `known`/`close` — знакомство героя, `relation` — активная связь с главным участником (`kind`), `given` — человек из области, если жив и в окружении. **Отличие от плана:** `anyCandidate(ctx, name, role, when, scope)` получает имя роли — для `pick: given` кандидат берётся из области по имени. `checkRoles` уже отказывает в именах `hero`, `protagonist` и плейсхолдеров подлежащего.
- `text/`: `renderTemplate(ctx, template, scope, seq, slot) → TextPart[]` — `{name}`, `{he}`… от `protagonist`, `{role}` ссылкой, `{role.he}`, `{role.age}`… (`{role.name}` нет — это `{role}`); `seq`, `slot` пока не используются. `checkEventTemplate(template, {roles})`. Схема `grammar:` по контракту (`text/grammar.ts`): символ → список строк или `{text, when}`.

## D-190. Подбор ролей: поиск с возвратом, выбор по весам
2026-10-16 · принято (задача 3.3); исполняет D-041, D-056, D-161

**Контекст.** «Первый подходящий» (3.1) мог занять роль человеком, которого единственного ждала следующая роль: `canFillRoles` говорил «да», а запуск события — отказ.

**Решение.**
- `canFillRoles` и `fillRoles` опираются на один чистый перебор `feasible`: можно ли заполнить роли с данного места при данной области. `canFillRoles` — ответ перебора с нуля; случайность не тратит.
- `fillRoles` идёт по ролям по порядку и для каждой берёт случайного кандидата (`weightedPick` из мирового потока `state.rng`) только среди тех, при ком остальные роли ещё заполнимы. Поэтому, если `canFillRoles` ответил «да», `fillRoles` не откажет; при отказе (`null`) случайность не тратится. Одна роль — один бросок.
- Вес кандидата — 720720 × множители `prefer`, у которых `when` выполнен для кандидата (дробь `n/d` — целым делением вниз, не меньше 1). 720720 делится на малые знаменатели, дробь с малым знаменателем (2…12, 16 и т. п.) точна; несколько дробей подряд или большой знаменатель округляются вниз, это допустимо для весов.
- Необязательная роль остаётся пустой, если никто не подходит или если с ней остальные роли не заполнить. Человек, не подошедший необязательной `given`-роли под `where`, остаётся в области и ранним ролям недоступен, ролям ниже — доступен. Роль, объявленная ниже, не видит пустую: условие со ссылкой на отсутствующую роль не выполнено.
- Пул: окружение героя (D-056), живые; `known`/`close` — знакомство героя (`scope.hero`) с кандидатом; `relation` + `kind` — активная связь вида `kind` с главным участником. Люди из области (герой, главный участник, прежние роли и все `given`) роли не получают.
- `given`: человек из области; умер, ушёл из окружения, не подходит под `where` или уже занят другой ролью (в том числе совпадает с главным участником) — отказ, если роль не `optional`.
- `anyCandidate` — по-настоящему: есть ли кандидат, подходящий под `where` роли и под `when`. `where` видит ту область, которую передали; роли выше, нужные `where`, вызывающий кладёт в область (3.2 при весе события по роли, пока роли не заполнены, видит только встроенные).

**Последствия.** Формат состояния не менялся, `SAVE_VERSION` прежний. Перебор — до k-й степени числа кандидатов при k ролях. Безнадёжный случай (поздняя обязательная роль некем не заполняется) отсекается сразу: до перебора проверяется (необходимое условие), что следующие обязательные роли, чей `where` не ссылается на ещё не заполненные роли, могут получить разных людей (паросочетание, алгоритм Куна; люди необязательных `given`-ролей считаются свободными), в том числе когда двум ролям нужен один-единственный человек (замер ревью: 45 человек, 3 широкие роли + соперник, которого нет, — было ~850 мс, теперь доли миллисекунды; случай «две роли на одного человека» было десятки секунд). Заполнимый случай находит ответ с первых веток. Если у события станет заметно больше ролей — вернуться к этому решению.

## D-195. Компактная запись сохранения
2026-10-16 · принято (задача 3.14); исполняет D-285, бюджет D-113 и D-166 прежний

**Решение.**
- Сохранение — `{version, shapes, state}` (`save/compact.ts`). `shapes` — таблица наборов ключей объектов состояния; объект пишется массивом: номер набора, затем значения в порядке ключей. Массив, первый элемент которого — число или метка `"#"`, пишется с `"#"` впереди; остальные массивы — как есть. Строки, числа, `null` и логические значения не меняются.
- Преобразование общее, без знания о модулях: новые части состояния сжимаются сами, правка `save/` при этом не нужна. Порядок ключей сохраняется, поэтому `deserialize(serialize(s))` равно `s`, и повторное сохранение даёт тот же текст.
- `version` остаётся полем верхнего уровня: сохранение любого другого формата, в том числе прежнего несжатого, отвергается по версии до разбора (D-058). `SAVE_VERSION` = 9 (D-169). Ошибки разбора (`shapes` не список, неизвестный номер, не то число значений, объект вне таблицы, ключ `__proto__`) — `corrupt`, без исключения.
- Метрика `saveBytes` и раньше мерила `serialize` — меряет сжатую запись без правок.
- Без gzip и словаря строк: таблица строк (имена, id, `journal`) дала бы ещё ~0,7 МБ, но ссылку на строку пришлось бы отличать от числа в каждом поле. Это следующий шаг, если контент этапов 4+ снова подведёт к 2 МБ.

**Замер** (10 прогонов × 300 лет, seeds 1–10): сохранение 2,15–2,33 МБ (медиана 2,18) → 1,29–1,38 МБ (медиана 1,32), −39%; время прогона без изменений (медиана −0,1 с).

**Последствия.** Сохранение в `localStorage` нечитаемо глазами без `deserialize`. Бюджет 2 МБ выполнен с запасом ~0,6 МБ под контент 3.13 и этапа 4. `serialize` на 300 лет — ~45 мс вместо ~15 (автосохранение после каждой команды этого не замечает), зато строка в `localStorage` (UTF-16) ~2,6 МБ вместо ~4,4 — дальше от квоты браузера.
- Сжатие держится на том, что у записей постоянный набор ключей. Карта по id (`{c12: …, c45: …}`) в состоянии даст каждой такой карте свой набор: без потерь, но таблица наборов раздуется. Такие данные лучше хранить списком записей.

## D-200. Тексты событий: разбор, грамматика, поток текста
2026-10-16 · принято (задача 3.4); исполняет D-046, D-162, D-163; уточняет D-172 (шестой аргумент `renderTemplate`, поля `optional` и `symbols` в `TemplateEnv` — обратно совместимые добавления)

**Решение.**
- Один разбор для проверки и показа — `text/template.ts` (без сборочных файлов): `{name}`, `{role}`, `{role.he}`, `{role?…}` (вложенные `{}` допустимы), `<symbol>`, `<Symbol>`. Одиночные `<` и `>` — ошибка «unbalanced».
- Формулировка символа выбирается равномерно среди тех, у кого нет `when` или `when` выполнен для главного участника (`conditionReport`, без случайности). У каждого символа обязана быть формулировка без `when`. Свои символы события (`own`, шестой необязательный аргумент `renderTemplate`) закрывают общие с тем же именем.
- Поток текста — `seedRng(seed, textStream(seq, slot))`, хеш номера события и места текста (`option.0.result`…), один генератор на текст; создаётся только когда в тексте есть символ, мировой поток не тратится.
- `checkEventTemplate(template, {roles, optional?, symbols?})`: `optional` — роли, которые могут остаться пустыми, их можно писать только внутри `{role?…}`; `symbols` — если задано, проверяется определённость символов. Проверку событий 3.2 вызывает без `symbols`/`optional`: их проверяет `checkGrammar` (общая грамматика, свои грамматики событий, символы и необязательные роли в текстах событий), поэтому ошибка не дублируется.
- Формулировка с `when`, не выполненным или скрытым (`conditionReport(...).met` false), не подходит: тайна через текст не раскрывается. Необязательная роль в формулировке пишется только внутри `{role?…}`.
- Циклы ищет `grammarProblems`; в показе — предохранитель глубины 16.
- `ownLine(parts, subjectId)` — в `text/text.ts`: «Name » и «Name was » снимаются, первая буква заглавная; «Name's…», «Name, aged…», чужой субъект — без изменений.

## D-230. Темп рассказчика: шанс от длительности действия
2026-10-16 · принято (задача 3.7); исполняет D-168, уточняет D-170 и порядок D-045 (между продолжениями и историями встаёт «вне очереди со дна», D-233)

**Решение.**
- Шанс события в день зависит от номинальной длительности действия — середины его `duration` (бросок длительности при старте рассказчик не видит, он лежит только как `endDay`). Действие от `longActionDays` (по умолчанию 60) бросает `longActionChancePer10k`, короче — `eventChancePer10k`. Это и есть деление D-168: на коротких действиях 0–1 события, на длинных 2–4.
- Порядок дня: продолжения на сегодня (`stories.dueEvents`, раньше любого темпа) → минимальный промежуток → вне очереди «со дна» (D-233) → шанс дня → события открытых историй, если хоть одно подходит, иначе колода. Событие истории не смешивается с колодой: обещанное продолжение идёт первым.
- Колода героя: нет `followup_only`, `deck: backstory`, `who: npc`; `once: game` — по `lastFired` (запись остаётся навсегда), `once: life` — по списку текущего главы (сбрасывается, когда `playerId` сменился: хука смены главы у рассказчика нет, обновление ленивое); повтор — `cooldown_days` события или `eventRepeatCooldownDays`. События со `story` весят `storyWeight`.
- Контракт со `stories/` (для 3.8): рассказчик запускает каждое событие из `dueEvents` по порядку (тихое извещение не мешает остальным, но броска колоды в этот день уже нет); умерших главных участников пропускает. Запущенное в очереди не помечается: признак запуска — `lastFired[eventId]`, `dueEvents` обязан его учитывать. Рассказчик не работает в день конца действия (`actionEndPhase` выходит раньше), поэтому срок «сегодня» надо отдавать и на следующий день (просроченные включительно). `once` и `lastFired` записывает `launch`; события, запущенные вне рассказчика, записывать должна 3.8.
- Дно и напряжение принадлежат роду, а не главе: наследник их наследует (`bottomSince`, `tension` не сбрасываются при смене главы).
- Событие запускает `fireEvent` (D-181): тихое извещение тоже получает паузу и запись в `lastFired`.
- Числа в `content/narrator.yaml`: 200 на коротких, 600 на длинных, промежуток 10 дней. По ним 10 прогонов на нынешнем контенте дают цель D-168 (цифры — в CHANGELOG); после перевода событий (3.12) числа подбираются заново по метрикам.

**Последствия.** `SAVE_VERSION` = 5: в состоянии рассказчика появились напряжение, список `once: life`, дни «дна», счётчики. Тесты 3.2, которым нужен бросок колоды для событий `followup_only`, снимают это поле.

## D-210. Ключи условий персонажа и здоровья: причины и скрытость
2026-10-16 · принято (задача 3.5); исполняет D-043, D-054; уточняет D-032, D-037

**Решение.**
- Условия: `traits_any` (есть хоть одна из черт), `traits_none` (нет ни одной), `stats: {martial: {min, max}}` (характеристики такие, как сегодня: с чертами, образованием, возрастом и ранами — `stats()`), `fame_min` (1–3), `conditions_any`, `conditions_none` (состояния здоровья).
- Причины недоступности — в контенте: `names.reasons` (`traits_any`, `traits_none`, `stat_min`, `stat_max`, `fame_min`; плейсхолдеры `{traits}`, `{stat}`, `{value}`, `{fame}`) и `names.stats` (названия характеристик); для состояний — `health.texts.conditions_any`, `conditions_none` (`{conditions}`). Все поля обязательны, плейсхолдеры проверяются при загрузке.

Состояния здоровья не скрываются.
- Валидатор проверяет неизвестные черты и состояния в любом `when` и `where` действий, событий и общей грамматики.

## D-211. Эффекты `stats` и `fame`

**Решение.** `stats: {martial: 1}` меняет базу характеристики (не итоговое значение) и держит её в 0…20 (`BASE_STAT_MAX`, верх шкалы `names.statScale`); инвариант персонажа проверяет тот же диапазон. `fame: n` — сдвиг шага известности на −3…3 (не 0), итог остаётся в 0…3. ## D-212. Эффект `kill` и проверка права на смерть героя
2026-10-16 · принято (задача 3.5); исполняет D-164; уточнено D-174

**Решение.**
- `kill: <cause>` кладёт `{characterId, cause}` в `state.deathRequests`; для уже умершего запрос не создаётся (а умерший между запросом и фазой смерти — отбрасывается самой фазой). Причины насилия — `killed_in_duel`, `killed` в `health.causes` (текст «He had fallen in a duel.», «He had been killed.»).
- Валидатор (`health/content.ts`) считает героем цель `effects` в событии не `who: npc`, `on: {hero: …}` в любом событии и `on: {protagonist: …}` в событии не `who: npc`; прочие роли берутся из окружения и героем не бывают. Для героя `kill` допустим только в `failure` варианта с `check` события `severity: heavy` и только в исходе без `next`; то же для `kill` внутри `later`. В остальных случаях — ошибка. Для людей мира — любой исход. У `deck: backstory` проверку делает 3.11. В действиях (`actions`) `kill` запрещён: они всегда идут за героя. Неизвестная причина — ошибка.

**Последствия.** Формат состояния и `SAVE_VERSION` не менялись. Хроника прогона не изменилась: контент событий не трогали.


## D-220. Ключи условий и эффектов для мнений, связей и тайн
2026-10-16 · принято (задача 3.6); исполняет D-035…D-037, D-121, D-123, D-162, D-172

**Решение.** Условия (`relations/conditions.ts`; проверяются для персонажа условия, второй человек — роль области):
- `opinion: {toward: <роль>, min?, max?}` — мнение персонажа о роли в границах (нужна хотя бы одна, `min ≤ max`);
- `relation: {kind, with: <роль>}` и `relation_none: {kind, with}` — есть/нет действующей связи этого вида с ролью, в любом порядке пары (для несимметричной «покровитель» без различия сторон: сторона — отдельный ключ, если понадобится, пока нет);
- `acquainted: known|close` — насколько герой знает персонажа условия (у самого героя выполнено всегда; `close` включает `known`).

Эффекты (`relations/effects.ts`; применяются к персонажу своего блока, порядок: `opinion_end`, `opinion`, `relation`, `secret`, `reveal`, `introduce`):
- `opinion: [{toward, reason, value?}]` — `addOpinionReason` (повтор ещё действующей причины обновляет её);
- `opinion_end: [{toward, reason}]` — убрать причину (D-225);
- `relation: [{start|end: kind, with, reason?}]` — начать связь (персонаж блока — покровитель, `a`) или закончить действующую; `reason` (только с `end`) — id причины конца, по умолчанию `event`;
- `secret: {kind, known_by: [роли]}` — тайна о персонаже; знает её он сам и названные роли;
- `reveal: {kind, to: [роли]}` — названные роли узнают тайны персонажа этого вида (нет такой тайны — ничего);
- `introduce: known|close` — герой знакомится с персонажем (`introduce`, уровень не понижается; для самого героя пропускается).

Реестры ссылок на роли: `toward`, `with`, `known_by`, `to` — поэтому проверка событий ловит неизвестную роль и в `where`/`prefer` ролей («роль ссылается на роль ниже» — плохой пример `roles-ref-below.yaml`, подмена в `tests/roles-refs.test.ts` убрана, D-192).

**Последствия.** `SAVE_VERSION` и формат состояния не менялись. ▸ ставится как прежде (ключ `relation` в исходе, D-183).

## D-221. Пустая роль и необслуживаемые случаи: пропуск, не исключение
2026-10-16 · принято (задача 3.6); закрывает замечание 3.2 о необязательных ролях

**Решение.** Роль, которую область не содержит (необязательная осталась пустой): эффект, называющий её, **пропускается**, а условие, называющее её, **не выполнено, причина скрыта** (вариант не показывается, кандидат не подходит; текста причины нет, потому что назвать некого). Остальные пропуски без ошибок: человек сам с собой (`toward` на себя), мёртвый (новая связь), связь уже существует (`start`) или не существует (`end`), оба человека вне окружения героя (данные хранятся только для окружения, D-063). Бросает только то, что проверяет загрузка контента (неизвестный вид связи, причина, роль), и вызовы API модуля напрямую, как в 2.4.

**Почему.** Событие с необязательной ролью — обычный случай (`witness`), ошибка в нём ломала бы прогон; пропущенный эффект виден автору в тесте события, а исключение — только игроку, в середине партии.

## D-222. Скрытая причина и тексты причин; проверка ссылок в событиях

## D-174. События людей мира не меняют героя
2026-10-16 · принято (ведущая сессия этапа 3, вопрос из 3.5); исполняет D-047, уточняет D-164, D-212

**Контекст.** D-212 по букве D-164 допускает `on: {hero: {kill}}` в исходе `failure` тяжёлого события `who: npc`. Но в событии человека мира выбирает он, а не игрок, и шанса игрок не видит. D-047 уже решил шире: герой в роли событий людей мира не попадает, всё, что затрагивает героя, — событие героя, где человек мира — роль, а его инициатива — вес по его чертам.

**Решение.**
- Эффекты на героя — блок `on.hero`, `relation` с `with: hero`, `hero` в `secret.known_by`, `reveal.to`, `schedule.roles`, эффект `introduce` (герой знакомится с персонажем) — включая вложенные `later`.
- В событиях `who: npc` такие эффекты запрещены валидатором. Роль `hero` в эффектах там допустима только в `opinion` и `opinion_end` (`toward: hero`) — это чувства самого человека мира.
- В событиях `who: both` они допустимы, но применяются, только когда главный участник — сам герой (выбирает игрок); когда событие досталось человеку мира, они пропускаются (по смыслу похоже на пустую роль, D-221, но делается по списку ключей — см. ниже).
- Условия на героя (`where`, `when` с `toward: hero`) не ограничены: это чтение мира, а не изменение.
- Делает 3.9 в `events/`: валидатор для `who: npc` и пропуск для `who: both` по списку ключей выше. Это не D-221 буквально: убрать `hero` из области нельзя (перестанут работать условия на героя и `opinion toward: hero`), а `introduce` от области не зависит.

**Последствия.** D-164 и D-212 для героя-главного участника не меняются: `kill` героя через `effects`, `on.hero` или `on.protagonist` в событиях `who: hero|both` допустим только в `failure` тяжёлого события без `next`. В `who: npc` путь `on.hero` закрыт целиком. Вопрос из 3.5 в STATUS закрыт.

## D-176. Побочные строки исхода — после строки события

**Контекст.** Строки, которые пишут эффекты исхода (начало и конец связи героя, D-223; смена черты, D-081), появляются в хронике раньше строки самого события, которая пишется в конце (D-180): следствие стоит перед причиной. Так было уже в этапе 2 со сменой черты.

**Решение.** Пока идёт событие, строки, которые пишут эффекты его исходов о герое и участниках, копятся в ожидающем событии и пишутся сразу после строки события, в порядке появления. Делает 3.9 (владеет `events/` и `chronicle/log.ts` в волне 4).

**Последствия.** Порядок записей в хронике меняется; отбор и уровни строк (D-130) — прежние. 3.9 решает и записывает: уровень побочной строки — в момент эффекта (как сейчас, по деньгам и повторам D-130); если строка события не сохраняется (`log` вернул `null`, событие человека мира без `chronicle: true`, D-166), накопленные строки пишутся как обычно, без неё. Новое поле ожидающего события поднимает `SAVE_VERSION` (D-169).

## D-240. Продолжения: своя очередь модуля историй
2026-10-16 · принято (решение Тима, задача 3.8); исполняет D-044, меняет последствие D-053 «в ту же очередь»

**Контекст.** План 3.8 и D-053 говорили «через очередь назначенного `state.scheduled`». Но эта очередь принадлежит `time/`: фаза «назначенное» применяет из неё эффекты и ничего не знает о событиях; править `time/` задача 3.8 не может.

**Решение.**
- Назначенные события лежат в своей части состояния `stories/`: `state.followups` — `{eventId, protagonist, given, dueDay, offered}`, по порядку дней (при равных — по порядку назначения). Смысл тот же, что у D-053: переживает сохранение, смерть главного участника отменяет его записи (хук `storiesOnDeath`).
- Эффект `schedule: [{event, after_days: {min, max}, roles?: {новая_роль: роль}, protagonist?: роль}]` — на персонажа блока (или на роль `protagonist`). Срок бросается из мирового потока в момент эффекта (`min = max` — без броска). Люди ролей передаются под новыми именами для ролей `pick: given`; пустая роль не передаётся, пустая роль `protagonist` пропускает продолжение (D-221). Так же работает внутри `later`: область сохранена (D-171).

## D-241. Истории: открытие, закрытие событием, срок
2026-10-16 · принято (задача 3.8); исполняет D-044; уточнено D-178

**Решение.**
- Эффект `story: {open, days, fallback?: [id], roles?: {новая_роль: роль}}` открывает историю персонажа блока: `state.openStories` — `{id, owner, openedDay, deadline, fallback, given}`. Открытие уже открытой истории начинает её заново (новый срок и люди).
- История закрывается событием со `story: <id>`, сработавшим после открытия, в том числе в тот же день (история открыта из `later` или тихой развязки до рассказчика): при открытии запоминается `lastFired` событий истории (`seen`), изменение — признак (D-230). Исключение: тихое извещение истории, которое само открывает её заново, закроет новую сразу (`lastFired` пишется после исхода) — такое событие писать не нужно. Рассказчик запускает события историй только для героя, поэтому так закрываются только истории героя; истории людей мира закрываются сроком или смертью. Если 3.9 будет запускать события со `story` для людей мира, ей нужно смотреть `isStoryOpen` и закрывать историю (сейчас для этого нет вызова — заметка в STATUS).
- В день срока (или позже, если в тот день фаза не работала — день конца действия) — первая подходящая запасная развязка: привязка к действию, `when` по владельцу, `once`, заполнимость ролей с людьми истории. Её запускает фаза историй (`fireEvent`) с людьми истории как `given` и пишет `lastFired` (и `lifeFired` для `once: life`, D-230). Ни одной — история закрывается молча. Смерть владельца закрывает его истории, в том числе героя (наследование — этап 4).
- **Пробел (для ведущей сессии):** рассказчик считает вес события истории и запускает его без людей истории — `eventWeight` и `launch` не получают `given`. Поэтому событие истории из колоды рассказчика может брать только роли `circle`/`known`/`close`/`relation`; роль `pick: given` (обязательная) делает его невозможным. Люди истории доходят только до запасной развязки. Готов `storyGiven(state, characterId, storyId)`; правка — в `events/` (`eventWeight(…, given)`) и `narrator/` (передать `storyGiven` в вес и в `launch`), это модули 3.9.

## D-242. Передача продолжений рассказчику и отмена
2026-10-16 · принято (задача 3.8); исполняет D-044, D-230

**Решение.**
- Фаза историй (перед рассказчиком) каждый день: убирает продолжения, которые рассказчик уже запустил (`lastFired[event] ≥ offered`); у остальных сбрасывает `offered`; затем каждое продолжение со сроком сегодня или раньше проверяет — главный участник жив, роли заполнимы (`canFillRoles` с переданными людьми) — и помечает `offered = сегодня` (одно на событие в день, чтобы признак запуска был однозначным). `dueEvents` отдаёт помеченные сегодня, по порядку. Если рассказчик не дошёл до продолжения (раньше ждало другое) — завтра оно снова передаётся.
- Роли не заполнить — отмена со строкой журнала `kind: followup_cancelled`: «{name}'s business with {other} came to nothing.», где other — переданный человек, умерший или ушедший из окружения; иначе «{name}'s plans came to nothing.». Тексты в коде: у историй нет своего ключа контента (вынести можно отдельной задачей).
- `when` и привязка к действию у продолжения не проверяются, как и в `fireEvent`: продолжение — обещание, его условия — роли.
- Запасную развязку запускает фаза историй, не рассказчик: она пишет только `lastFired`/`lifeFired`, но не промежуток (`lastEventDay`), напряжение и счётчики темпа (`narratorStats`). Тяжёлая развязка напряжение не поднимает, событие колоды может выпасть на следующий день. Если это станет заметно — рассказчику (модуль 3.9 в волне 4) отдать функцию учёта, а фазе историй её звать.

## D-250. Бросок людей мира: один шанс на окружение

**Решение.** Каждый день (в фазе рассказчика, до разбора событий героя, и когда герой без действия тоже) один бросок `narrator.npcChancePer10k` (0 по умолчанию; в контенте 150, около 5 событий в год). ## D-300. Портрет героя
2026-10-16 · принято (решение Тима, идея I-002); уточнено D-177, D-301

**Контекст.** GDD §1 и §15 говорили «без графики». Тим хочет живое лицо героя, которое делает игру выразительнее.

**Решение.**
- В игре есть портрет героя: пиксельное лицо в две краски, чуть подробнее Doom (не дизеринг и не ASCII). Это единственная графика; карт-картинок и звука по-прежнему нет. GDD §1 и §15 поправлены, добавлен §8.10.
- Игрок внешность не настраивает: нет настройки лица, одежды и внешности, нет отдельного выбора внешности или народности ради лица. Происхождение из предыстории (D-167, 3.11) остаётся как есть; лицо учитывает его как последствие. Лицо целиком следует из происходящего в игре и в истории рода. ## D-301. Портреты разные: варианты каждой детали от генов человека
2026-10-16 · принято (решение Тима, к I-002); уточняет D-300

**Контекст.** Портрет строится из деталей. Если у каждой детали один вариант, у всех людей со шрамом будет один и тот же шрам, и лица станут похожи.

**Решение.**
- Каждая деталь лица (форма головы, глаза, брови, нос, рот, уши, волосы, борода, морщины, шрамы, повязки, аксессуары) — не меньше трёх вариантов; плюс небольшие сдвиги положения и пропорций.

**Последствия.** Критерии задач портрета этапа 4: тест, что у 100 разных людей со шрамом шрамы не все одинаковые, и что лицо одного человека стабильно во времени (кроме возраста и новых состояний).

## D-178. События истории из колоды приходят с людьми истории
2026-10-16 · принято (задача 3.1d, ведущая сессия); закрывает пробел D-241, уточняет D-244

**Решение.**
- `eventWeight(ctx, event, protagonist, given = {})`: переданные люди (роли `pick: given`) учитываются при заполнимости ролей, но не в условиях веса. Рассказчик для события истории берёт из `storyGiven(state, герой, история)` только людей его ролей `pick: given`, считает с ними вес и запускает событие с теми же людьми. ## D-270. Предыстория: устройство и порядок сцен
2026-10-16 · принято (задача 3.11); исполняет D-038, D-167, D-187

**Решение.**
- Ключ `backstory:` (`content/backstory/backstory.yaml`): `base` — нейтральная база основателя (все шесть характеристик), `stages` — стадии по порядку (`id`, `scenes` — сколько сцен стадии идёт подряд, по умолчанию 1, `offer`), `texts.leave` — строка «вышел в мир». Сцена — событие `deck: backstory` с `stage`; среди сцен стадии берётся одна по весу `eventWeight` (условия и роли должны проходить), уже показанная не повторяется; стадия без подходящей сцены пропускается.
- Состояние `state.backstory` = `{running, founder, stage, inStage, offered, played}` (`SAVE_VERSION` = 8). Новая партия (`backstoryOnNewGame`): основатель получает базу, `traits = []`, запускается первая сцена. После выбора (`backstoryAfterChoice`, D-187) — следующая; когда стадии кончились — строка `kind: backstory_end` и `awaiting_action`. Если героем стал не основатель, предыстория сбрасывается: наследник сцен не проходит. Без ключа `backstory` в контенте поведение прежнее (случайный основатель, D-055).
- `worldOnNewGame` заполняет окружение до первой сцены (`refillCircle`); первая фаза мира находит его полным и только заводит годовые часы.
- Строка `start` больше не называет возраст («comes into the world»): возраст основателя в начале — `settings.startAge` 16–18, а выходит он в мир в 16–21 после `age_years` из сцен; возраст называет строка «вышел в мир» (`{age}`).

**Последствия.** Все партии начинаются иначе: поток случайности сдвинулся (окружение раньше, сцены), метрики этапа 2 сравнивать нельзя. Тесты, которые считали окружение пустым после `newGame`, чистят `state.circle` сами.

## D-271. Происхождение: предложенные варианты
2026-10-16 · принято (задача 3.11); исполняет D-167, D-179; правило о варианте без `when` и `count: 2` заменены D-188 (все 3 по случаю)

**Решение.** Стадия с `offer: {count, variants}` при входе тянет `count` вариантов из `variants` (мировой поток `state.rng`, без повторов) и кладёт их в `state.backstory.offered`. ## D-283. Лекарь: выбор по роли, проверка учёности лекаря не выражается форматом

**Решение.**
- В игре есть встречи с известными людьми: реальные люди прошлых веков и герои фольклора и старых книг, подходящие по эпохе, под своими именами, как пасхалки в вымышленном мире (GDD §5 не меняется: это намёк, а не точная история). Игрок встречает 1–2 таких за жизнь героя.
- Условия из обсуждения I-001 — обязательны: появление не по сценарию, а по совпадению года, места, возраста и роли героя (опора 1); знаменитость — персонаж мира со своими датами жизни, а не создаётся под событие (GDD §9); большую историю не меняет, только проходит мимо, даты жизни соблюдаются; авторские права — только реальные люди прошлых веков, фольклор и первоисточники давно умерших авторов, опубликованные больше 95 лет назад к выпуску, без экранизаций, современных книг и торговых марок; у фигуры в контенте поля «источник» и «почему можно»; список перед выпуском показать юристу.
- Где: механизм и первые 10–15 фигур разных культур (по несколько на державу) — этап 5: без мест условие «год, место, роль» не выполнить. Дополнения списка — этап 7. Движок этапа 3 уже даёт нужное: событие героя с ролью знаменитости, `once: game`, условия на роль. Портреты знаменитостей можно рисовать вручную (I-002, этап 4+); раздел «Встречи» в итоге рода (D-016) — возможное развитие.

**Последствия.** Architect включает механизм и первый список в план этапа 5; риски из I-001 (дорогой контент, «парад знаменитостей», узнаваемость зависит от культуры игрока) — в критерии: не чаще 1–2 встреч за жизнь героя, проверка по прогонам.

## D-193. Проверка по характеристике роли: `check.of`
2026-10-16 · принято (задача 3.1g, вопрос из 3.12); исполняет D-165, уточняет D-042, D-182

**Решение.**
- У проверки есть необязательное поле `of: <роль>`: проверяется характеристика этого человека, а не главного участника (Учёность лекаря, который лечит героя). Надбавки `bonus` тоже смотрят на него: условие `when` надбавки проверяется по человеку роли. Встречная проверка (`against`) с `of` меряет характеристику роли против характеристики другой роли.
- Роль в `of` должна быть известна событию. Она может быть `optional` (лекаря в окружении может не быть, D-283): пока такая роль пуста, вариант скрыт — как вариант, чьё условие называет пустую роль (D-221). Поэтому для правила «в сцене есть вариант без `when`» такой вариант считается условным. Роль встречной проверки (`against`) по-прежнему не `optional` (D-182) и не совпадает с `of`. Плохие примеры `event-check-of-unknown-role.yaml`, `event-check-of-optional-only.yaml`.
- Исход проверки по-прежнему ложится на главного участника (`effects`), людям ролей — через `on`.

**Последствия.** Контент лекаря пишет `check: { stat: learning, of: physician, difficulty: N }`; 3.13 переводит на это `fever` и `npc_fever`, где 3.12 оставила лечение без броска, а условие-заглушку `opinion: {toward: physician, min: -100}` можно убрать. Формат сохранения не меняется.

## D-194. Индекс персонажей по id
2026-10-16 · принято (задача 3.1h, замер 3.12 в D-285)

**Контекст.** После контента 3.12 прогон на 300 лет — 24–35 с при бюджете 30 с. Профиль: 16% собственного времени — `characterById` (`world/`), около 1,8 млн вызовов за 50 лет; двоичный поиск разбирает id на каждом шаге.

**Решение.** `findCharacter` (`helpers.ts`) держит индекс «id → место в `state.characters`» — кэш вне состояния (`WeakMap` по массиву), в сохранение не попадает. Персонажи только добавляются, поэтому индекс дописывает новых; загруженное сохранение приносит новый массив и получает свой индекс. Если массив изменили на месте иначе (так игра не делает) — простой поиск, как раньше, и индекс строится заново. `characterById` (`world/`) зовёт `findCharacter`.

**Последствия.** Прогон быстрее на 30–40% (150 лет, seed 1: 10,7–11,1 с → 6,6–7,6 с на одной машине); хроника и журнал совпадают с main байт в байт. Случайность и формат сохранения не меняются.

## D-201. Общий тип «сущность»: первая задача этапа 4
2026-10-16 · принято (решение Тима, идея I-005; проверила ведущая сессия этапа 3); формат ссылки в хронике (D-020, D-130) решает architect этапа 4

**Решение.** До рода, первой задачей этапа 4, — общий шаблон сущности для рода, мест, держав, долгов и отряда: префикс id через `newId` и реестр видов, ссылка в хронике на сущность любого вида, страница с учётом видимости (обобщение `pages/` — сейчас страницы только у людей). Объём минимальный: только то, что нужно двум первым видам этапа 4 (род и, например, долг); общий «движок сущностей» на все случаи не строится. Конкретику решает architect в плане этапа 4, в том числе формат ссылки `{id, name}`: вид можно выводить из префикса id, а лишнее поле в каждой ссылке увеличит сохранение (в хронике ~8000 строк, D-285, D-195). Изменение формата — новой записью, уточняющей D-020.

**Почему.** Этапы 4–6 добавят пять видов сущностей; без общего шаблона каждая задача сделает ссылки и страницы по-своему, а сводить потом дороже.

## D-202. Журнал команд и версия контента в сохранении
2026-10-16 · принято (решение Тима, идеи I-006 и I-007); уточняет D-140, D-003

**Решение.**
- Одна задача первой волны этапа 4. Рядом с сохранением хранится журнал партии: seed, версия контента (хеш содержимого `content/`) и список команд (`start`, `choose`). Журнал воспроизводит партию на той же версии контента: для сообщений о багах («пришли историю»), регрессионных тестов и разбора партий Тима. Сохранению не замена: при другой версии контента история расходится (D-003).
- Версия контента пишется и в сохранение. Если сохранение не прошло проверку на новом контенте (пропал id события, черты, состояния), игра говорит, что контент игры изменился, а не «не удалось прочитать» (сейчас по D-140 — общее «could not be read»), даёт сохранить журнал для отчёта и начинает новую партию. Журнал — вторая ячейка хранилища рядом с сохранением (D-140 говорит об одной); если задача меняет формат состояния, поднимает `SAVE_VERSION` (D-058, D-169). Сохранение, прошедшее проверку, грузится и при другой версии контента — без предупреждения на каждую правку.

**Почему.** Сейчас при пропавшем id `readSave` отбрасывает сохранение как `corrupt`, и игра сообщает «could not be read» — причина непонятна. Хеш сам по себе мало что даёт: правки контента без удаления id сохранения не ломают; ценен он как часть журнала команд.

## D-203. Ворота по метрикам в CI
2026-10-16 · принято (решение Тима, идея I-008; согласие Тима на правку CI); задача 3.15; уточняет D-019, D-065, D-113 (ориентиры становятся проверкой CI)

**Решение.**
- Отдельная работа CI прогоняет 300 лет на закреплённых seeds 1…N (те же, что в замерах этапов; N = 10, если работа укладывается в ~6 мин, иначе меньше — записано в файле коридоров) и валит PR только по числам, которые не зависят от машины: нарушения инвариантов, максимум сохранения > 2 МБ (D-113), медиана строк хроники на жизнь главы вне 25–45 (D-019, D-065; после закрытия этапа 3).
- Строки хроники сначала идут в отчёт без провала: сейчас медиана ~59, её подрезает 3.13. Провал по ним включает ведущая сессия при закрытии этапа 3 — с коридором, на котором этап закрылся (25–45 или решение Тима, если 3.13 цель не возьмёт).
- Время прогона, медиана смерти главы, число глав, событий в год — в отчёте без провала: время на серверах CI скачет, а медиана смерти между этапами законно движется.
- Коридоры и признак «валит / только отчёт» — в одном файле со ссылками на решения, меняются вместе с записью DECISIONS.

**Почему.** Параллельные сессии двигают общие числа (3.12 вывела время к 27 с при пределе 30 с, сохранение за 2 МБ); сейчас это замечают только при замерах задач.

## D-286. Критерий «механика не бессмысленна»
2026-10-16 · принято (решение Тима); дополняет правило «Соавторство» (`.claude/rules/workflow.md`)

**Решение.** Каждая новая механика называет три вещи: что игрок (или мир) решает, что это стоит и что меняется в игре. Механика без последствий, украшение «чтобы было», не добавляется. Architect проверяет это при плане этапа и задачи, reviewer — в дифф PR.

**Последствия.** В IDEAS.md у каждой идеи пишется «смысл». В чек-лист reviewer добавлен пункт, в план architect — шаг. Идея, у которой нет смысла, уходит в «отклонена» или дорабатывается.
